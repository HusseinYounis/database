10  Storage & Indexing

Chapter 10

10.1 Why Storage Matters

Chapter 11 (Query Processing) will show you how a query executes. But all execution happens ultimately by reading pages from disk into memory. The number of page reads is the primary cost metric for query optimization — and indexes exist to reduce that count dramatically.

10.2 Storage Hierarchy

10.3 Why We Need a Buffer Manager

Whenever a database uses data, that data must exist in memory (RAM) — because the CPU can only work with data that is loaded there. Accessing data in RAM is fast (nanoseconds), but RAM is expensive and limited in size. A typical database can be hundreds of gigabytes or even terabytes, and it is simply impossible to fit all of it in memory at once.

Disks (HDDs or SSDs) solve the capacity problem — they are cheap and can store enormous amounts of data permanently. But there is a catch: accessing data on disk is thousands of times slower than accessing data in RAM.

This creates a fundamental tension:

Storage Speed Size Cost
RAM Very fast (ns) Small Expensive
Disk Very slow (ms) Huge Cheap

The database needs a module that bridges this gap — something that:

  • Loads data from disk into RAM on demand (when a query needs it)
  • Keeps frequently used data in RAM so it does not have to be re-read from disk
  • Writes modified data back to disk to make it permanent
  • Decides which data to evict from RAM when memory is full and new data needs to come in

This is exactly the job of the Buffer Manager.

10.4 What Does the Buffer Manager Do?

The DBMS buffer manager sits between RAM and disk. It maintains a pool of pages in RAM — called the database buffer — and is responsible for the following:

  • Allocates buffer space in main memory so that data blocks can be temporarily stored there while in use.
  • Returns the address of a requested data block if that block is already present in the database buffer (no disk access needed).
  • Fetches missing blocks from disk into the buffer when a requested data block is not currently in memory.
  • Evicts older blocks from the buffer when there is no free space available, making room for newly requested blocks.
  • Writes dirty blocks to disk before evicting them — if an evicted block was recently modified, its changes must be saved to disk first; otherwise it is simply discarded.
  • Re-fetches evicted blocks from disk storage back into the buffer if a user later requests data that was previously removed.

10.4.1 How It All Works Together

The diagram below traces what happens when you run a SQL query — from the moment the query arrives to when results are returned (and how modified data is synced back to disk).

TipKey Takeaway
  • The first time you query data → it comes from disk (slow)
  • The second time you query the same data → it comes from the buffer in RAM (fast — no disk access!)
  • If you modify data → the change happens in the buffer first, then gets written back to disk to make it permanent
ImportantThe Page is the Unit of I/O

All disk reads and writes transfer exactly one page (typically 4–16 KB, configurable). Reading a single 10-byte row forces a full page to come into RAM. Query cost is measured in number of page I/Os, not rows accessed.

10.5 Records and Page Layout

Every table in a relational database is stored on disk. But disk and memory work differently — the CPU can only process data that is in memory (RAM), and disk stores data in fixed-size chunks. To bridge this, three concepts stack on top of each other:

  • A record is one row (the database’s smallest unit of meaning)
  • A page is a fixed-size block (the disk’s smallest unit of transfer, typically 4–16 KB)
  • A file is a sequence of pages that stores all records of one table

When the DBMS decides how to store a table, it must answer four questions — in this exact order:

  1. What type of file? — heap or sorted?
  2. How are pages organized in the file? — linked list or page directory?
  3. How are records organized on each page? — packed, bitmap, or slotted?
  4. How is each record formatted? — fixed-length or variable-length?

10.5.1 1 — Types of Files

The file type determines how pages (and the records inside them) are ordered. The DBMS picks the type that gives the lowest I/O cost for the table’s typical workload.

1 I/O = reading or writing exactly 1 page between disk and memory.

Heap File — “Throw it anywhere”

Records and pages are stored in no particular order. New records go into any page that has free space.

Operation Cost (N = number of pages)
Full scan N
Search by key N (must scan everything)
Insert ≈ 2 (find a free page + write it)
Delete Search cost + 1 write
  • ✅ Very cheap inserts
  • ❌ Search always costs a full scan

Sorted File — “Keep it in order”

Pages are ordered and records within each page are sorted by a key field. This makes binary search possible.

┌──────────────────────────────────────────────────────┐
│  Sorted File  (sorted by ID)                          │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐           │
│  │  Page 1  │  │  Page 2  │  │  Page 3  │  ...      │
│  │  ID: 1   │  │  ID: 51  │  │  ID: 101 │           │
│  │  ID: 2   │  │  ID: 52  │  │  ID: 102 │           │
│  │  ...     │  │  ...     │  │  ...     │           │
│  │  ID: 50  │  │  ID: 100 │  │  ID: 150 │           │
│  └──────────┘  └──────────┘  └──────────┘           │
│  Records always in sorted order → binary search works │
└──────────────────────────────────────────────────────┘
Operation Cost (N = number of pages)
Full scan N
Search by key \log_2 N (binary search)
Insert \log_2 N + N (find spot + shift records to maintain order)
Delete \log_2 N + N
  • ✅ Fast searches
  • ❌ Expensive inserts — shifting records to keep order can touch every page
TipWhich file type should you use?

Choose based on the most common operation:

  • Mostly inserts + full scans (e.g., logs, events) → Heap File
  • Mostly searches by key (e.g., user lookup by ID) → Sorted File

In practice, most real tables use heap files and add indexes (like B+ trees) on top to speed up searches without the insert cost of sorted files.

10.5.2 2 — How Pages Are Organized in a File

Regardless of file type, the DBMS must track which pages have free space for inserting new records. There are two standard implementations:

Linked List Implementation

A header page at the start points to two separate linked lists of data pages:

  • Full pages list — pages that have no room left
  • Free pages list — pages that still have space

Each data page stores pointers to the next and previous pages in its list, plus a free-space tracker.

┌─────────────────┐
│   Header Page   │
└────┬────────────┘
     │
     ├──→  Full Pages:  [Page 3] ←→ [Page 1] ←→ [Page 6] ←→ ...
     │
     └──→  Free Pages:  [Page 5] ←→ [Page 2] ←→ [Page 4] ←→ ...
                         ↑
                    (has free space)

To insert a new record: scan the free-pages list until a page with enough room is found.

  • ✅ Simple to implement
  • ❌ In the worst case, you must scan all free pages — expensive when the file is large

Page Directory Implementation

Only the header pages are linked together. Each header page holds a list of entries, where each entry says: “Data page X has Y bytes of free space”.

┌──────────────────┐      ┌──────────────────┐
│   Header Page 1  │ ───→ │   Header Page 2  │ ───→ ...
│                  │      │                  │
│ [Page 1 | 120B]  │      │ [Page 4 | 400B]  │
│ [Page 2 |   0B]  │      │ [Page 5 |  88B]  │
│ [Page 3 |   0B]  │      │ [Page 6 | 212B]  │
└──────────────────┘      └──────────────────┘
        ↓                         ↓
  (data pages              (data pages
   stored here)             stored here)

To insert a new record: read header pages only — each entry already tells you how much space is available on each data page. No need to touch data pages at all until you find the right one.

  • ✅ Much faster than linked list for inserts
  • ✅ Scales well — even with thousands of pages, you only read a few header pages
ImportantCounting I/Os with Header Pages

When a question gives you the specific implementation (linked list or page directory), include header page reads in your I/O count. If no implementation is specified, ignore header page cost.

10.5.3 3 — How Records Are Organized on a Page

Now we look inside one page. How are the individual records laid out? The answer depends on whether records are fixed-length or variable-length.

Pages with Fixed-Length Records

Every record is the same size, so the DBMS knows exactly where each one is. Two layouts exist:

Packed layout — records are stored back-to-back with no gaps.

┌──────────────────────────────────────────────┐
│ Page Header (# records = 3)                   │
├──────────┬──────────┬──────────┬─────────────┤
│ Record 1 │ Record 2 │ Record 3 │  Free Space  │
└──────────┴──────────┴──────────┴─────────────┘
  ← records grow this way →          ↑ next insert goes here
  • Insert: next position = (# records) × (record size)
  • Delete: must shift all later records left by one to fill the gap (keeps it packed)

Unpacked layout (Bitmap) — the page header stores a bitmap. Each bit = one slot. 1 = occupied, 0 = free.

┌────────────────────────────────────────────────────┐
│ Page Header  [bitmap: 1 1 0 1 0 0 ...]             │
├──────────┬──────────┬──────────┬──────────┬────────┤
│ Record 1 │ Record 2 │  empty   │ Record 4 │  ...   │
└──────────┴──────────┴──────────┴──────────┴────────┘
                            ↑
                    slot 3 is free (bit = 0)
  • Insert: find first 0 bit → write record there → set bit to 1
  • Delete: set that slot’s bit to 0 — no shifting needed

Pages with Variable-Length Records (Slotted Page)

When records can have different sizes (e.g., VARCHAR fields), a slotted page layout is used. The key idea is:

  • Records are stored from the top of the page downward
  • A slot directory lives at the bottom of the page and grows upward
  • Free space stays in the middle between records and slot directory
┌─────────────────────────────────────────────┐  ← top of page
│           Page Header                        │
│  (page_id, free space pointer, ...)          │
├─────────────────────────────────────────────┤
│  Record 1  (e.g., 42 bytes)                 │
├─────────────────────────────────────────────┤
│  Record 2  (e.g., 28 bytes)                 │
├─────────────────────────────────────────────┤
│  Record 3  (e.g., 55 bytes)                 │
├─────────────────────────────────────────────┤
│                                             │
│           F R E E   S P A C E              │
│                                             │
├─────────────────────────────────────────────┤
│ ... │ (ptr₃, len₃) │ (ptr₂, len₂) │ (ptr₁, len₁) │ free ptr │ slot count │
└─────────────────────────────────────────────┘  ← bottom of page
                ↑  Slot Directory (grows upward)

The slot directory contains:

Field What it stores
Slot count Total number of slots (filled + empty)
Free space pointer Byte offset of the next free position
Entry per slot (record pointer, record length)

Insert: write the record at the free space pointer → add a new (pointer, length) entry in the slot directory.

Delete: set the slot entry to null (pointer = null, length = null) → the space is reclaimed later during compaction (periodically, live records are repacked to merge gaps).

NoteWhy use a slot directory?

Every record is identified by a Record ID = (page number, slot number). Indexes store these Record IDs to point to records. If a record moves within the page (e.g., during compaction), only its slot entry changes — the Record ID stays the same. This keeps all indexes valid without any updates.

10.5.4 4 — Record Formats

This is the innermost level: how are the bytes of a single record laid out?

Fixed-Length Records (FLR)

Every field has a known, fixed size. All records of the same schema occupy exactly the same number of bytes.

Schema: Employee(id INTEGER, age INTEGER, salary FLOAT, active BOOLEAN)

┌──────────────┬──────────────┬──────────────┬──────────┐
│  id          │  age         │  salary      │  active  │
│  4 bytes     │  4 bytes     │  4 bytes     │  1 byte  │
└──────────────┴──────────────┴──────────────┴──────────┘
 offset 0       offset 4       offset 8       offset 12

Total record size = 4 + 4 + 4 + 1 = 13 bytes (every record, always)

To find field i: \text{offset} = \sum_{j=0}^{i-1} \text{size}(j)

Standard field sizes:

Type Size
INTEGER 4 bytes
FLOAT 4 bytes
BOOLEAN 1 byte
CHAR(N) N bytes
DATE 8 bytes
VARCHAR(N) ≤ N bytes (variable!)
  • ✅ Simple and fast — no overhead needed
  • ❌ CHAR(50) storing "Ali" wastes 47 bytes

Variable-Length Records (VLR)

A VLR contains at least one variable-length field (VARCHAR, TEXT). Since we don’t know the exact size at schema time, the record uses a record header to store pointers to the end of each variable-length field. Fixed-length fields always come first.

Schema: Person(name VARCHAR(20), age INTEGER, city VARCHAR(15))

┌─────────────────────┬───────────────┬──────────────────────┐
│   Record Header     │  Fixed Fields │  Variable Fields      │
│  (end-of-var ptrs)  │  age: 4 bytes │  name  │  city        │
│  [ptr_name|ptr_city]│               │  "Ali" │  "Cairo"     │
└─────────────────────┴───────────────┴──────────────────────┘
                                         ↑ actual bytes stored
                                         only 3 + 5 = 8 bytes,
                                         not 20 + 15 = 35 bytes

Layout rule: fixed-length fields first, then variable-length fields in order.

  • ✅ Space-efficient — stores only what is needed
  • ❌ Requires reading the record header to find variable fields
Note

Regardless of format, every record has a unique Record ID = (page #, slot #) that the DBMS uses to locate it directly from disk.

FLR VLR
Field sizes All fixed Mix of fixed + variable
Record size Same for all records Varies per record
Example fields INT, FLOAT, CHAR(N) VARCHAR, TEXT
Find field i Offset = sum of prior sizes Read record header first
Space usage May waste space Uses only what’s needed

10.5.5 Solved Example — Page Capacity and Scan Cost

Note📝 Solved Example

Problem: An Employee table has 80,000 records. Each record is fixed-length with the following fields:

Field Size
Ssn 9 bytes
Fname 15 bytes
Lname 15 bytes
Salary 8 bytes
Dno 4 bytes

Page size = 4 KB (4,096 bytes). Page header occupies 96 bytes.

(a) How many records fit on one page? (b) How many pages does the table occupy? (c) What is the I/O cost of a full table scan?

Solution:

(a) Record size = 9 + 15 + 15 + 8 + 4 = 51 bytes

Usable space per page = 4096 − 96 = 4000 bytes

\text{Records per page} = \left\lfloor \frac{4000}{51} \right\rfloor = 78 \text{ records/page}

(b) Pages needed:

\text{Pages} = \left\lceil \frac{80{,}000}{78} \right\rceil = \left\lceil 1025.6 \right\rceil = 1026 \text{ pages}

(c) A full table scan reads every page:

\text{I/O cost} = 1026 \text{ page reads}

If a disk read takes ~5 ms, the scan takes ≈ 5.1 seconds. A B+ tree index on Ssn would reduce the same lookup to 3–4 page reads ≈ 0.02 ms.

10.6 What is Database Indexing?

Imagine a huge database as a giant list of records. Searching through this list without an index is like looking for a needle in a haystack — you’d have to check each record one by one. But with an index, it’s like having a roadmap that shows you exactly where to look!

An index in a database is a special data structure that stores pointers to the actual data in a way that makes retrieving information much faster. It’s like a catalog that helps you find what you’re looking for without scanning everything.

10.6.1 Real-Life Example: Finding a Customer’s Order

Let’s say you run an e-commerce website and you need to find a customer’s order. Your database might look like this:

Order ID Customer Name Product Amount
3 Ahmed Smartphone $500
1 Fatima Laptop $1200
2 Omar Headphones $150
4 Ahmed Tablet $300
5 Youssef Camera $700
6 Layla Watch $200
7 Fatima Keyboard $100
8 Kareem Monitor $400
9 Omar Charger $50
10 Youssef Laptop Stand $30

10.6.2 How Search Works Without an Index

Caution❌ Full Table Scan (No Index)

To find Omar’s orders, the database must check every single row from top to bottom:

  1. Row 1 — Ahmed? ✗   skip
  2. Row 2 — Fatima? ✗   skip
  3. Row 3 — Omar? ✓   found → save Row 3
  4. Row 4 — Ahmed? ✗   skip
  5. Row 5 — Youssef? ✗   skip
  6. Row 6 — Layla? ✗   skip
  7. Row 7 — Fatima? ✗   skip
  8. Row 8 — Kareem? ✗   skip
  9. Row 9 — Omar? ✓   found → save Row 9
  10. Row 10 — Youssef? ✗   skip

10 rows checked to find 2 results. With 10 million rows, that means 10 million comparisons — the cost grows linearly with table size: O(n).

10.6.3 How Search Works With an Index

Tip✅ Index Lookup (With Index on Customer Name)

The index keeps Customer Name values sorted. To find Omar:

  1. The database opens the index (a sorted structure — B+ tree).
  2. It performs a binary search / tree traversal directly to "Omar".
  3. It reads the stored pointer: Omar → Order IDs {2, 9}.
  4. It fetches only those 2 rows from the data file.

2 rows fetched, ~3–4 index steps regardless of table size. Cost grows logarithmically: O(\log n).

The index on Customer Name looks like this internally:

Customer Name Order IDs
Ahmed 3, 4
Fatima 1, 7
Kareem 8
Layla 6
Omar 2, 9

10.6.5 Solved Example — Index Speedup Calculation

Note📝 Solved Example

Problem: A university has a Students table with 500,000 rows stored in a heap file. A registrar needs to find all course registrations for student S00142. The database measures:

  • Full table scan time: 10 seconds
  • B+ tree index height on student_id: h = 4
  • Each page read takes 0.02 ms

(a) How many page reads does the full scan require? (b) How many page reads does the indexed lookup require (assume 3 matching rows on 2 pages)? (c) What is the speedup factor?

Solution:

Assume page size 4 KB, record 100 bytes → 20 records/page.

(a) Full scan: \text{Pages} = \left\lceil \frac{500{,}000}{20} \right\rceil = 25{,}000 \text{ page reads} \text{Time} = 25{,}000 \times 0.02\,\text{ms} = 500\,\text{ms} \approx 0.5\,\text{s}

(b) Index lookup: h + data pages = 4 + 2 = 6 page reads \text{Time} = 6 \times 0.02\,\text{ms} = 0.12\,\text{ms}

(c) Speedup: \text{Speedup} = \frac{25{,}000}{6} \approx 4{,}167\times \text{ faster}

This is why indexes are critical for large OLTP tables.

10.7 File Organization in Indexing

File organization refers to how data and indexes are physically stored in memory or on disk. The choice of file organization directly determines which index types are applicable, how efficiently the DBMS can locate records, and what the cost of each query operation will be.

The following are the common types of file organizations used in indexing:

10.7.1 Heap File

NoteHeap Organization

Records are stored in insertion order — no sorting, no grouping. New rows are simply appended to the end of the file.

  • Access: Full table scan required to find any record → O(n)
  • Best for: Bulk loading data, write-heavy tables, full-table analytics
  • Index compatibility: Any index type can be built on top of a heap file; the index itself provides the ordering
  • Limitation: Without an index, every query reads every page
Heap File (unsorted):
┌──────────────────────────┐
│ Fatima | Laptop   | 1200 │  ← inserted first
│ Omar   | Headsets | 150  │
│ Ahmed  | Phone    | 500  │
│ Layla  | Watch    | 200  │  ← inserted last
└──────────────────────────┘

10.7.2 Sequential (Sorted) File

NoteSequential Organization

Records are stored sorted by a key (the ordering field). Finding a record by that key can use binary search.

  • Access: Binary search on ordering key → O(\log n) pages
  • Best for: Range queries on the sort key (WHERE salary BETWEEN 3000 AND 7000)
  • Index compatibility: A sparse index works perfectly — one index entry per page block
  • Limitation: Insertions are expensive (must maintain sort order); only one sort order possible
Sequential File (sorted by Customer Name):
┌──────────────────────────┐
│ Ahmed  | Phone    | 500  │  ← A
│ Fatima | Laptop   | 1200 │  ← F
│ Kareem | Monitor  | 400  │  ← K
│ Omar   | Headsets | 150  │  ← O  ← binary search lands here
│ Youssef| Camera   | 700  │  ← Y
└──────────────────────────┘

10.7.3 Hash File

NoteHash Organization

Records are placed into buckets determined by a hash function h(\text{key}) \mod B, where B is the number of buckets.

  • Access: Equality lookup → O(1) theoretical (one bucket access)
  • Best for: Exact-match equality queries (WHERE id = 42)
  • Index compatibility: Pairs naturally with a hash index
  • Limitation: Range queries are impossible — hashing destroys sort order; overflow buckets degrade performance
Hash File (hash on Order ID, B = 3):
Bucket 0: │ Order 3 │ Order 6 │ Order 9  │
Bucket 1: │ Order 1 │ Order 4 │ Order 7  │ Order 10 │
Bucket 2: │ Order 2 │ Order 5 │ Order 8  │

10.7.4 Clustered File

NoteClustered Organization

Records are physically stored in the same order as the primary index (usually a B+ tree). The data file is the index leaf level.

  • Access: Range queries read consecutive pages → minimizes I/O
  • Best for: Range queries + sorted output on the clustering key
  • Index compatibility: The table can have only one clustered index (one physical sort order)
  • MySQL InnoDB: Every table is always a clustered B+ tree ordered by the primary key
Clustered File (clustered on Customer Name):
B+ Tree leaf pages:
Page 1: │ Ahmed, Phone, $500 │ Ahmed, Tablet, $300 │
Page 2: │ Fatima, Laptop, $1200 │ Fatima, Keyboard, $100 │
Page 3: │ Kareem, Monitor, $400 │ Layla, Watch, $200 │
Page 4: │ Omar, Headsets, $150 │ Omar, Charger, $50 │

10.7.5 Summary: File Organizations at a Glance

Organization Physical Order Equality Range Query Insert Cost Index Type
Heap Insertion order Scan O(n) Scan O(n) O(1) — append Any (index provides order)
Sequential Sorted by key Binary search O(\log n) Efficient on sort key O(n) — shift rows Sparse index ideal
Hash By h(key) O(1) Not supported O(1) avg Hash index
Clustered Matches B+ tree O(\log n) Excellent — consecutive pages O(\log n) + splits One clustered B+ tree

10.7.6 Solved Example — Choosing a File Organization

Note📝 Solved Example

Problem: A hospital Patients table stores 200,000 records. The following query patterns are observed:

Query Frequency
WHERE patient_id = 'P00512' Very high (lookup by PK)
WHERE age BETWEEN 30 AND 50 High (age-range reports)
WHERE department = 'Cardiology' High (department reports)
Bulk insert of 10,000 new admission records Daily

Recommend a file organization and justify your choice for each query.

Solution:

Query Recommended Organization Justification
Equality on patient_id Clustered (B+ tree on patient_id) O(\log n) — primary key lookup; InnoDB auto-clusters on PK
Range on age Sequential sorted by age, or secondary B+ tree index Range scan is O(\log n + k) with sorted file or B+ tree
Filter by department Secondary B+ tree index on department Unclustered index; if low-cardinality consider bitmap index
Bulk daily inserts Heap file append for staging O(1) insert; batch-load into main table after admission
Tip

In MySQL InnoDB, the table is always physically a clustered B+ tree on the primary key. All other access patterns are served by secondary unclustered indexes.

10.8 Index Concepts

An index is an auxiliary data structure that maps search key → record location (RID). It is separate from the data file and maintained automatically on INSERT/UPDATE/DELETE.

10.8.1 Index Entry Structure: Key → Value

Every entry in an index is a key–value pair:

Component What it holds
Key (search key) A copy of the indexed column(s) value — e.g., "Charlie", 42, "2024-01-15"
Value (data reference) A pointer to the actual row(s) in the main table — the Record ID (RID) = (page_id, slot_id)
NoteWhat the index actually stores
  • Copies of selected column values (the search key) — not the full row
  • Pointers to the actual data rows in the main table (RIDs), so the DBMS can fetch the full record when needed
  • The structure stays sorted (B+ tree) or hashed, allowing fast lookups without scanning the entire table

This is why adding an index trades a little extra storage and write overhead for dramatically faster reads.

10.9 Types of Indexing Methods

Indexes are classified along three independent dimensions: density, clustering, and key type. Understanding these helps you choose the right index for each query pattern.

10.9.1 Dense vs. Sparse Index

  • Dense Index
  • Sparse Index

A dense index has one index entry for every record in the data file.

  • Works on any file organization (heap or sorted)
  • Faster lookup — every record has a direct pointer
  • Higher storage cost — index grows with the data
Data File          Dense Index
───────────        ────────────────────
Ahmed  | p1,s1  ←  Ahmed  → (p1,s1)
Fatima | p1,s2  ←  Fatima → (p1,s2)
Kareem | p2,s1  ←  Kareem → (p2,s1)
Omar   | p2,s2  ←  Omar   → (p2,s2)

A sparse index has one index entry per page (data block), not per record.

  • Requires the data file to be sorted on the index key
  • Much smaller index — fits in fewer pages
  • Lookup: find the correct page via index, then scan within the page
Data File (sorted)   Sparse Index
──────────────────   ─────────────────
Page 1: Ahmed        Ahmed  → page 1
        Fatima       Kareem → page 2
Page 2: Kareem       Omar   → page 3
        Layla
Page 3: Omar
        Youssef
Note

B+ trees in practice use a hybrid approach: sparse at internal levels (routing keys only), dense at the leaf level (one pointer per record).

10.9.2 Clustered vs. Unclustered Index

ImportantClustered Index

The physical order of data rows matches the index order. Reading a range of index entries also reads consecutive pages.

  • A table can have only one clustered index
  • In MySQL InnoDB, the primary key is always the clustered index
  • Secondary indexes store the primary key as their RID — one extra lookup per row (“index dive”)

10.10 Unclustered Index

The index order does not match the data order. Each index pointer may point to a different page.

  • Many unclustered indexes allowed per table
  • Range queries may cause one page I/O per row — expensive at scale
Clustered Unclustered
Range query (k rows) ~k / records_per_page pages Up to k separate pages
Equality query ~height pages ~height pages
Build cost High (file must be sorted) Lower
Count per table Only one Many allowed

10.10.1 Primary vs. Secondary Index

Type Defined on Key property
Primary index The ordering key of a sequential/clustered file One entry per distinct key value; non-duplicate
Secondary index Any non-ordering attribute Can have duplicate keys; always unclustered unless it matches the physical order
Tip

A secondary index is the workhorse of OLTP systems — it allows fast lookup on any column (email, phone, status) without reorganizing the data file.

10.10.2 Solved Example — Clustered vs. Unclustered I/O Cost

Note📝 Solved Example

Problem: An Employee table has 40,000 records stored across 2,000 pages (20 records/page). Department 4 (Dno = 4) has 4,000 employees.

  • In the clustered case: all Dno=4 employees occupy consecutive pages.
  • In the unclustered case: the 4,000 employees are randomly scattered (worst case: one per page).
  • B+ tree height h = 3 for both indexes.

Compute the I/O cost for: SELECT * FROM Employee WHERE Dno = 4

Solution:

Clustered B+ tree index on Dno: \text{Pages for Dno=4} = \left\lceil \frac{4{,}000}{20} \right\rceil = 200 \text{ pages} \text{Total I/O} = h + \text{data pages} = 3 + 200 = \mathbf{203} \text{ page reads}

Unclustered B+ tree index on Dno: \text{Worst case: each matching record on a different page} \text{Total I/O} = h + 4{,}000 = 3 + 4{,}000 = \mathbf{4{,}003} \text{ page reads}

Index Type I/O Cost Notes
Clustered 203 reads Sequential pages — disk-friendly
Unclustered up to 4,003 reads Random I/O — 20× more expensive
Full scan (no index) 2,000 reads Cheaper than unclustered for large selectivity!
Important

When selectivity is high (many matching rows), the optimizer may choose a full scan over an unclustered index because random I/O becomes more expensive than sequential I/O.

10.11 B-Tree and B+ Tree Index

Both B-Tree and B+ Tree are self-balancing tree structures used to keep data sorted and allow searches, insertions, and deletions in O(\log n) time. They are the foundation of indexing in virtually every major RDBMS.

10.11.1 B-Tree vs. B+ Tree: Key Differences

Feature B-Tree B+ Tree
Data pointers In all nodes (internal + leaf) Leaf nodes only
Internal nodes Store keys and data records Store keys only (routing)
Leaf nodes Not linked Linked as a doubly-linked list
Range queries Slower — may visit internal nodes Fast — scan leaf chain sequentially
Space efficiency Lower (data in every node) Higher (internal nodes hold more keys → larger fan-out)
Used in practice Rare (mostly theoretical) MySQL, PostgreSQL, Oracle, SQL Server
NoteWhy B+ Tree Won

Because internal nodes in a B+ Tree store only keys (no data), each internal node can hold far more keys — increasing the fan-out and reducing the tree height. A B+ Tree with order d = 100 over 100 million records has only 4 levels. Range scans are also trivial: follow the leaf chain without backtracking through the tree.

10.11.2 B+ Tree Structure

  • Balanced: all leaf nodes at the same depth h; guarantees O(\log n) operations
  • Order d: every internal node except the root holds between d and 2d search keys
  • All data pointers in leaves: internal nodes hold only keys for routing
  • Leaf chain: leaf nodes are linked in a doubly-linked list for sequential range scans

10.11.3 Cost Analysis

Operation I/O Cost Formula
Equality search h page reads h = \lceil \log_d n \rceil
Range scan (k results) h + \lceil k / f \rceil f = records per leaf page
Insert $h + $ splits Amortised O(1) splits
Delete $h + $ merges Rare in practice

Example: order d = 100, n = 10^8 records → h = \lceil \log_{100} 10^8 \rceil = 4 levels. Four page reads to find any record in a 100-million-row table.

10.11.4 Solved Example — B+ Tree Height and Search Cost

Note📝 Solved Example

Problem: A Transactions table has 50 million records. A B+ tree index of order d = 200 is built on the TransactionDate column. Each leaf page holds 200 records.

(a) Calculate the tree height h. (b) What is the I/O cost for an equality query (find transactions on a specific date, 5 matching records)? (c) What is the I/O cost for a range query returning 10,000 transactions? (d) How does this compare to a full table scan (20 records/page)?

Solution:

(a) Tree height: h = \left\lceil \log_{2d}\, n \right\rceil = \left\lceil \log_{400}\, 50{,}000{,}000 \right\rceil = \left\lceil \frac{\log 50{,}000{,}000}{\log 400} \right\rceil = \left\lceil \frac{7.699}{2.602} \right\rceil = \lceil 2.96 \rceil = \mathbf{3 \text{ levels}}

(b) Equality search (5 rows on 1–2 leaf pages): \text{I/O} = h + \text{leaf pages} = 3 + 1 = \mathbf{4 \text{ page reads}}

(c) Range scan (10,000 rows, 200 rows/leaf page): \text{Leaf pages} = \left\lceil \frac{10{,}000}{200} \right\rceil = 50 \text{I/O} = h + 50 = 3 + 50 = \mathbf{53 \text{ page reads}}

(d) Full table scan: \text{Pages} = \left\lceil \frac{50{,}000{,}000}{20} \right\rceil = 2{,}500{,}000 \text{ page reads}

Method I/O reads Relative cost
Equality + B+ tree 4 1×
Range (10K rows) + B+ tree 53 13×
Full table scan 2,500,000 625,000×

10.14 Hash Indexes

A hash index applies a hash function h(k) to map a key to a bucket where matching records are stored.

Characteristic Value
Equality search O(1) theoretical
Range query Impossible — hashing destroys order
Overflow Buckets chain when full

10.14.1 Extendible Hashing

Uses a global depth and a directory. When a bucket overflows: 1. Split only the full bucket (not all buckets) 2. Double the directory only when all buckets at that depth are full

Hash indexes are available as USING HASH in PostgreSQL and as MEMORY storage engine indexes in MySQL.

10.15 Bitmap Indexes

A bitmap index stores, for each distinct value v of the indexed column, a bit vector of length N (one bit per row), where bit i = 1 iff row i has value v.

10.15.1 Example

Table Employee with 8 rows and column Gender:

Row Ssn Gender
1 123 M
2 333 M
3 999 F
4 987 M
5 666 F
6 453 F
7 888 F
8 963 M

Bitmap index on Gender:

Value Bit vector
M 1 1 0 1 0 0 0 1
F 0 0 1 0 1 1 1 0

10.15.2 Bitwise Operations for Multi-Predicate Queries

Query: SELECT * FROM Employee WHERE Gender = 'F' AND Dno = 5
Bitmap Vector
Gender = 'F' 0 0 1 0 1 1 1 0
Dno = 5 1 0 1 0 1 0 1 0
AND result 0 0 1 0 1 0 1 0

Rows 3, 5, and 7 satisfy both conditions — determined by bitwise AND in a single CPU operation across the entire table.

10.15.3 When to Use Bitmap Indexes

Tip

Bitmap indexes are ideal for:

  • Low-cardinality columns: Gender, Status, Region (few distinct values → compact bitmaps)
  • Analytical / OLAP queries with many AND/OR column predicates
  • Data warehouse star-schema dimension columns (InnoDB does not support bitmap indexes natively — they are a first-class citizen of Oracle and PostgreSQL with specialized extensions)

Avoid bitmap indexes on: - High-cardinality columns (every value different → one bit vector per row = huge overhead) - OLTP tables with frequent writes — bit vectors must be updated on every INSERT/UPDATE/DELETE

10.15.4 Oracle Bitmap Index

-- Oracle natively supports bitmap indexes
CREATE BITMAP INDEX idx_emp_sex ON Employee(Gender);
CREATE BITMAP INDEX idx_emp_dno ON Employee(Dno);

-- Query: optimizer combines bitmaps with bitwise AND/OR automatically
SELECT * FROM Employee WHERE Gender = 'F' AND Dno = 5;

PostgreSQL does not have a native CREATE BITMAP INDEX, but the query planner performs bitmap index scans by combining multiple B+ tree indexes with BitmapAnd/BitmapOr operations internally.

10.17 Chapter Summary

ImportantKey Takeaways — Chapter 10

  1. All disk I/O transfers pages (4–16 KB). The buffer manager caches pages; the cost metric is page reads.

  2. File organizations: heap (insertion order), sequential (sorted), hash, clustered. MySQL InnoDB stores data in the clustered B+ tree (primary key order).

  3. Dense vs sparse: dense index has one entry per record; sparse index has one entry per page (requires sorted file).

  4. B+ tree: balanced, fan-out 2d, height h \approx \log_d n. All leaves linked for range scans. Supports equality, range, ORDER BY, and GROUP BY efficiently. With d = 100 and 10^8 records: only 4 page reads to find any record.

  5. Hash index: O(1) equality; completely useless for range queries.

  6. Bitmap index: per-distinct-value bit vectors; bitwise AND/OR answering multi-predicate analytical queries at CPU speed. Best for low-cardinality columns in OLAP.

  7. Composite indexes: leftmost prefix rule determines which predicates the index covers. A covering index includes all columns a query needs — eliminates all table lookups.

  8. Use EXPLAIN / EXPLAIN ANALYZE to verify that the optimizer selects the intended index.

## Why We Need a Buffer Manager

Whenever a database uses data, that data must exist in **memory (RAM)** — because the CPU can only work with data that is loaded there. Accessing data in RAM is fast (nanoseconds), but RAM is expensive and limited in size. A typical database can be hundreds of gigabytes or even terabytes, and it is simply **impossible to fit all of it in memory at once**.

**Disks** (HDDs or SSDs) solve the capacity problem — they are cheap and can store enormous amounts of data permanently. But there is a catch: accessing data on disk is **thousands of times slower** than accessing data in RAM.

This creates a fundamental tension:

| Storage | Speed | Size | Cost |
|---------|-------|------|------|
| RAM | Very fast (ns) | Small | Expensive |
| Disk | Very slow (ms) | Huge | Cheap |

The database needs a module that bridges this gap — something that:

- Loads data from disk into RAM **on demand** (when a query needs it)
- Keeps frequently used data in RAM so it does not have to be re-read from disk
- Writes modified data back to disk to make it permanent
- Decides **which data to evict** from RAM when memory is full and new data needs to come in

This is exactly the job of the **Buffer Manager**.

---

## What Does the Buffer Manager Do?

The DBMS **buffer manager** sits between RAM and disk.
It maintains a pool of pages in RAM — called the **database buffer** — and is responsible for the following:

- **Allocates buffer space** in main memory so that data blocks can be temporarily stored there while in use.
- **Returns the address** of a requested data block if that block is already present in the database buffer (no disk access needed).
- **Fetches missing blocks** from disk into the buffer when a requested data block is not currently in memory.
- **Evicts older blocks** from the buffer when there is no free space available, making room for newly requested blocks.
- **Writes dirty blocks to disk** before evicting them — if an evicted block was recently modified, its changes must be saved to disk first; otherwise it is simply discarded.
- **Re-fetches evicted blocks** from disk storage back into the buffer if a user later requests data that was previously removed.

## The Page is the Unit of I/O

All disk reads and writes transfer exactly **one page** (typically 4–16 KB, configurable).
Reading a single 10-byte row forces a full page to come into RAM.
Query cost is measured in **number of page I/Os**, not rows accessed.
:::

## Records and Page Layout

Every table in a relational database is stored on disk. But disk and memory work differently — the **CPU can only process data that is in memory (RAM)**, and disk stores data in fixed-size chunks. To bridge this, three concepts stack on top of each other:

```{mermaid}
%%| eval: true
%%| echo: false
flowchart TD
    F["🗂️ FILE<br/>(one file per table)"]
    P1["📄 Page 1"] 
    P2["📄 Page 2"]
    P3["📄 Page 3"]
    R1["📝 Record 1"] 
    R2["📝 Record 2"]
    R3["📝 Record 3"]
    R4["📝 Record 4"]
    F --> P1 & P2 & P3
    P1 --> R1 & R2
    P2 --> R3 & R4
```

- A **record** is one row (the database's smallest unit of meaning)
- A **page** is a fixed-size block (the disk's smallest unit of transfer, typically 4–16 KB)
- A **file** is a sequence of pages that stores all records of one table

When the DBMS decides how to store a table, it must answer four questions — in this exact order:

1. **What type of file?** — heap or sorted?
2. **How are pages organized in the file?** — linked list or page directory?
3. **How are records organized on each page?** — packed, bitmap, or slotted?
4. **How is each record formatted?** — fixed-length or variable-length?

---

### 1 — Types of Files

The **file type** determines how pages (and the records inside them) are ordered. The DBMS picks the type that gives the **lowest I/O cost** for the table's typical workload.

> **1 I/O = reading or writing exactly 1 page** between disk and memory.

#### Heap File — "Throw it anywhere"

Records and pages are stored in **no particular order**. New records go into any page that has free space.

```{mermaid}
%%| eval: true
%%| echo: false
flowchart LR
    subgraph HF["🗂️ Heap File"]
        direction LR
        subgraph P1["📄 Page 1"]
            direction TB
            C["Rec C"]
            E["Rec E"]
        end
        subgraph P2["📄 Page 2"]
            direction TB
            A["Rec A"]
            FR1["(free)"]
        end
        subgraph P3["📄 Page 3"]
            direction TB
            F["Rec F"]
            D["Rec D"]
        end
        subgraph P4["📄 Page 4"]
            direction TB
            B["Rec B"]
            FR2["(free)"]
        end
    end
    note["❗ No order — records appear in any sequence"]
```

| Operation | Cost (N = number of pages) |
|-----------|---------------------------|
| Full scan | $N$ |
| Search by key | $N$ (must scan everything) |
| Insert | ≈ 2 (find a free page + write it) |
| Delete | Search cost + 1 write |

- ✅ Very cheap inserts
- ❌ Search always costs a full scan

#### Sorted File — "Keep it in order"

Pages are ordered and records within each page are **sorted by a key field**. This makes binary search possible.

```
┌──────────────────────────────────────────────────────┐
│  Sorted File  (sorted by ID)                          │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐           │
│  │  Page 1  │  │  Page 2  │  │  Page 3  │  ...      │
│  │  ID: 1   │  │  ID: 51  │  │  ID: 101 │           │
│  │  ID: 2   │  │  ID: 52  │  │  ID: 102 │           │
│  │  ...     │  │  ...     │  │  ...     │           │
│  │  ID: 50  │  │  ID: 100 │  │  ID: 150 │           │
│  └──────────┘  └──────────┘  └──────────┘           │
│  Records always in sorted order → binary search works │
└──────────────────────────────────────────────────────┘
```

| Operation | Cost (N = number of pages) |
|-----------|---------------------------|
| Full scan | $N$ |
| Search by key | $\log_2 N$ (binary search) |
| Insert | $\log_2 N + N$ (find spot + shift records to maintain order) |
| Delete | $\log_2 N + N$ |

- ✅ Fast searches
- ❌ Expensive inserts — shifting records to keep order can touch every page

::: callout-tip
## Which file type should you use?

Choose based on the most common operation:

- **Mostly inserts + full scans** (e.g., logs, events) → **Heap File**
- **Mostly searches by key** (e.g., user lookup by ID) → **Sorted File**

In practice, most real tables use **heap files** and add **indexes** (like B+ trees) on top to speed up searches without the insert cost of sorted files.
:::

### 2 — How Pages Are Organized in a File

Regardless of file type, the DBMS must track **which pages have free space** for inserting new records. There are two standard implementations:

#### Linked List Implementation

A **header page** at the start points to two separate linked lists of data pages:

- **Full pages list** — pages that have no room left
- **Free pages list** — pages that still have space

Each data page stores pointers to the next and previous pages in its list, plus a free-space tracker.

```
┌─────────────────┐
│   Header Page   │
└────┬────────────┘
     │
     ├──→  Full Pages:  [Page 3] ←→ [Page 1] ←→ [Page 6] ←→ ...
     │
     └──→  Free Pages:  [Page 5] ←→ [Page 2] ←→ [Page 4] ←→ ...
                         ↑
                    (has free space)
```

**To insert a new record:** scan the free-pages list until a page with enough room is found.

- ✅ Simple to implement
- ❌ In the worst case, you must scan all free pages — expensive when the file is large

#### Page Directory Implementation

Only the **header pages** are linked together. Each header page holds a list of entries, where each entry says: *"Data page X has Y bytes of free space"*.

```
┌──────────────────┐      ┌──────────────────┐
│   Header Page 1  │ ───→ │   Header Page 2  │ ───→ ...
│                  │      │                  │
│ [Page 1 | 120B]  │      │ [Page 4 | 400B]  │
│ [Page 2 |   0B]  │      │ [Page 5 |  88B]  │
│ [Page 3 |   0B]  │      │ [Page 6 | 212B]  │
└──────────────────┘      └──────────────────┘
        ↓                         ↓
  (data pages              (data pages
   stored here)             stored here)
```

**To insert a new record:** read header pages only — each entry already tells you how much space is available on each data page. No need to touch data pages at all until you find the right one.

- ✅ Much faster than linked list for inserts
- ✅ Scales well — even with thousands of pages, you only read a few header pages

::: callout-important
## Counting I/Os with Header Pages

When a question gives you the specific implementation (linked list or page directory), **include header page reads in your I/O count**. If no implementation is specified, ignore header page cost.
:::

### 3 — How Records Are Organized on a Page

Now we look inside one page. How are the individual records laid out? The answer depends on whether records are **fixed-length** or **variable-length**.

#### Pages with Fixed-Length Records

Every record is the same size, so the DBMS knows exactly where each one is. Two layouts exist:

**Packed layout** — records are stored back-to-back with no gaps.

```
┌──────────────────────────────────────────────┐
│ Page Header (# records = 3)                   │
├──────────┬──────────┬──────────┬─────────────┤
│ Record 1 │ Record 2 │ Record 3 │  Free Space  │
└──────────┴──────────┴──────────┴─────────────┘
  ← records grow this way →          ↑ next insert goes here
```

- Insert: next position = `(# records) × (record size)`
- Delete: **must shift** all later records left by one to fill the gap (keeps it packed)

**Unpacked layout (Bitmap)** — the page header stores a bitmap. Each bit = one slot. `1` = occupied, `0` = free.

```
┌────────────────────────────────────────────────────┐
│ Page Header  [bitmap: 1 1 0 1 0 0 ...]             │
├──────────┬──────────┬──────────┬──────────┬────────┤
│ Record 1 │ Record 2 │  empty   │ Record 4 │  ...   │
└──────────┴──────────┴──────────┴──────────┴────────┘
                            ↑
                    slot 3 is free (bit = 0)
```

- Insert: find first `0` bit → write record there → set bit to `1`
- Delete: set that slot's bit to `0` — **no shifting needed**

#### Pages with Variable-Length Records (Slotted Page)

When records can have different sizes (e.g., `VARCHAR` fields), a **slotted page** layout is used. The key idea is:

- Records are stored **from the top of the page downward**
- A **slot directory** lives at the **bottom of the page** and grows upward
- Free space stays in the **middle** between records and slot directory

```
┌─────────────────────────────────────────────┐  ← top of page
│           Page Header                        │
│  (page_id, free space pointer, ...)          │
├─────────────────────────────────────────────┤
│  Record 1  (e.g., 42 bytes)                 │
├─────────────────────────────────────────────┤
│  Record 2  (e.g., 28 bytes)                 │
├─────────────────────────────────────────────┤
│  Record 3  (e.g., 55 bytes)                 │
├─────────────────────────────────────────────┤
│                                             │
│           F R E E   S P A C E              │
│                                             │
├─────────────────────────────────────────────┤
│ ... │ (ptr₃, len₃) │ (ptr₂, len₂) │ (ptr₁, len₁) │ free ptr │ slot count │
└─────────────────────────────────────────────┘  ← bottom of page
                ↑  Slot Directory (grows upward)
```

The slot directory contains:

| Field | What it stores |
|-------|---------------|
| **Slot count** | Total number of slots (filled + empty) |
| **Free space pointer** | Byte offset of the next free position |
| **Entry per slot** | `(record pointer, record length)` |

**Insert:** write the record at the free space pointer → add a new `(pointer, length)` entry in the slot directory.

**Delete:** set the slot entry to `null` (pointer = null, length = null) → the space is reclaimed later during **compaction** (periodically, live records are repacked to merge gaps).

::: callout-note
## Why use a slot directory?

Every record is identified by a **Record ID = (page number, slot number)**. Indexes store these Record IDs to point to records. If a record moves within the page (e.g., during compaction), only its slot entry changes — the Record ID stays the same. This keeps all indexes valid without any updates.
:::

### 4 — Record Formats

This is the innermost level: how are the bytes of a single record laid out?

#### Fixed-Length Records (FLR)

Every field has a known, fixed size. All records of the same schema occupy **exactly the same number of bytes**.

```
Schema: Employee(id INTEGER, age INTEGER, salary FLOAT, active BOOLEAN)

┌──────────────┬──────────────┬──────────────┬──────────┐
│  id          │  age         │  salary      │  active  │
│  4 bytes     │  4 bytes     │  4 bytes     │  1 byte  │
└──────────────┴──────────────┴──────────────┴──────────┘
 offset 0       offset 4       offset 8       offset 12

Total record size = 4 + 4 + 4 + 1 = 13 bytes (every record, always)
```

To find field $i$: $\text{offset} = \sum_{j=0}^{i-1} \text{size}(j)$

Standard field sizes:

| Type | Size |
|------|------|
| `INTEGER` | 4 bytes |
| `FLOAT` | 4 bytes |
| `BOOLEAN` | 1 byte |
| `CHAR(N)` | N bytes |
| `DATE` | 8 bytes |
| `VARCHAR(N)` | ≤ N bytes *(variable!)* |

- ✅ Simple and fast — no overhead needed
- ❌ `CHAR(50)` storing `"Ali"` wastes 47 bytes

#### Variable-Length Records (VLR)

A VLR contains at least one variable-length field (`VARCHAR`, `TEXT`). Since we don't know the exact size at schema time, the record uses a **record header** to store pointers to the end of each variable-length field. Fixed-length fields always come first.

```
Schema: Person(name VARCHAR(20), age INTEGER, city VARCHAR(15))

┌─────────────────────┬───────────────┬──────────────────────┐
│   Record Header     │  Fixed Fields │  Variable Fields      │
│  (end-of-var ptrs)  │  age: 4 bytes │  name  │  city        │
│  [ptr_name|ptr_city]│               │  "Ali" │  "Cairo"     │
└─────────────────────┴───────────────┴──────────────────────┘
                                         ↑ actual bytes stored
                                         only 3 + 5 = 8 bytes,
                                         not 20 + 15 = 35 bytes
```

Layout rule: **fixed-length fields first**, then **variable-length fields** in order.

- ✅ Space-efficient — stores only what is needed
- ❌ Requires reading the record header to find variable fields

::: callout-note
Regardless of format, every record has a unique **Record ID = (page #, slot #)** that the DBMS uses to locate it directly from disk.
:::

| | **FLR** | **VLR** |
|-|---------|---------|
| Field sizes | All fixed | Mix of fixed + variable |
| Record size | Same for all records | Varies per record |
| Example fields | INT, FLOAT, CHAR(N) | VARCHAR, TEXT |
| Find field $i$ | Offset = sum of prior sizes | Read record header first |
| Space usage | May waste space | Uses only what's needed |

### Solved Example — Page Capacity and Scan Cost

::: callout-note
## 📝 Solved Example

**Problem:** An `Employee` table has 80,000 records. Each record is fixed-length with the following fields:

| Field | Size |
|-------|------|
| Ssn | 9 bytes |
| Fname | 15 bytes |
| Lname | 15 bytes |
| Salary | 8 bytes |
| Dno | 4 bytes |

Page size = 4 KB (4,096 bytes). Page header occupies 96 bytes.

**(a)** How many records fit on one page?
**(b)** How many pages does the table occupy?
**(c)** What is the I/O cost of a full table scan?


**Solution:**

**(a)** Record size = 9 + 15 + 15 + 8 + 4 = **51 bytes**

Usable space per page = 4096 − 96 = 4000 bytes

$$\text{Records per page} = \left\lfloor \frac{4000}{51} \right\rfloor = 78 \text{ records/page}$$

**(b)** Pages needed:

$$\text{Pages} = \left\lceil \frac{80{,}000}{78} \right\rceil = \left\lceil 1025.6 \right\rceil = 1026 \text{ pages}$$

**(c)** A full table scan reads every page:

$$\text{I/O cost} = 1026 \text{ page reads}$$

If a disk read takes ~5 ms, the scan takes ≈ **5.1 seconds**. A B+ tree index on `Ssn` would reduce the same lookup to **3–4 page reads** ≈ 0.02 ms.
:::

## What is Database Indexing?

Imagine a huge database as a giant list of records. Searching through this list without an index is like looking for a needle in a haystack — you'd have to check each record one by one. But with an **index**, it's like having a roadmap that shows you exactly where to look!

An **index** in a database is a special data structure that stores pointers to the actual data in a way that makes retrieving information much faster. It's like a catalog that helps you find what you're looking for without scanning everything.

### Real-Life Example: Finding a Customer's Order

Let's say you run an e-commerce website and you need to find a customer's order. Your database might look like this:

| Order ID | Customer Name | Product | Amount |
|----------|---------------|---------|--------|
| 3 | Ahmed | Smartphone | $500 |
| 1 | Fatima | Laptop | $1200 |
| 2 | Omar | Headphones | $150 |
| 4 | Ahmed | Tablet | $300 |
| 5 | Youssef | Camera | $700 |
| 6 | Layla | Watch | $200 |
| 7 | Fatima | Keyboard | $100 |
| 8 | Kareem | Monitor | $400 |
| 9 | Omar | Charger | $50 |
| 10 | Youssef | Laptop Stand | $30 |

### How Search Works Without an Index

::: callout-caution
## ❌ Full Table Scan (No Index)

To find Omar's orders, the database must check **every single row** from top to bottom:

1. Row 1 — Ahmed? ✗ &nbsp; skip
2. Row 2 — Fatima? ✗ &nbsp; skip
3. Row 3 — Omar? ✓ &nbsp; **found** → save Row 3
4. Row 4 — Ahmed? ✗ &nbsp; skip
5. Row 5 — Youssef? ✗ &nbsp; skip
6. Row 6 — Layla? ✗ &nbsp; skip
7. Row 7 — Fatima? ✗ &nbsp; skip
8. Row 8 — Kareem? ✗ &nbsp; skip
9. Row 9 — Omar? ✓ &nbsp; **found** → save Row 9
10. Row 10 — Youssef? ✗ &nbsp; skip

**10 rows checked** to find 2 results. With 10 million rows, that means **10 million comparisons** — the cost grows linearly with table size: $O(n)$.
:::

### How Search Works With an Index

::: callout-tip
## ✅ Index Lookup (With Index on Customer Name)

The index keeps `Customer Name` values **sorted**. To find Omar:

1. The database opens the index (a sorted structure — B+ tree).
2. It performs a **binary search / tree traversal** directly to `"Omar"`.
3. It reads the stored pointer: Omar → Order IDs `{2, 9}`.
4. It fetches **only those 2 rows** from the data file.

**2 rows fetched, ~3–4 index steps** regardless of table size. Cost grows logarithmically: $O(\log n)$.
:::

### Sorted Reference Table (Index Structure)

The index on `Customer Name` looks like this internally:

| Customer Name | Order IDs |
|---------------|-----------|
| Ahmed | 3, 4 |
| Fatima | 1, 7 |
| Kareem | 8 |
| Layla | 6 |
| Omar | 2, 9 |
| Youssef | 5, 10 |

### Solved Example — Index Speedup Calculation

::: callout-note
## 📝 Solved Example

**Problem:** A university has a `Students` table with 500,000 rows stored in a heap file. A registrar needs to find all course registrations for student `S00142`. The database measures:

- Full table scan time: **10 seconds**
- B+ tree index height on `student_id`: **h = 4**
- Each page read takes **0.02 ms**

**(a)** How many page reads does the full scan require?
**(b)** How many page reads does the indexed lookup require (assume 3 matching rows on 2 pages)?
**(c)** What is the speedup factor?


**Solution:**

Assume page size 4 KB, record 100 bytes → **20 records/page**.

**(a)** Full scan:
$$\text{Pages} = \left\lceil \frac{500{,}000}{20} \right\rceil = 25{,}000 \text{ page reads}$$
$$\text{Time} = 25{,}000 \times 0.02\,\text{ms} = 500\,\text{ms} \approx 0.5\,\text{s}$$

**(b)** Index lookup: **h + data pages = 4 + 2 = 6 page reads**
$$\text{Time} = 6 \times 0.02\,\text{ms} = 0.12\,\text{ms}$$

**(c)** Speedup:
$$\text{Speedup} = \frac{25{,}000}{6} \approx 4{,}167\times \text{ faster}$$

This is why indexes are critical for large OLTP tables.
:::

## File Organization in Indexing

**File organization** refers to how data and indexes are physically stored in memory or on disk. The choice of file organization directly determines which index types are applicable, how efficiently the DBMS can locate records, and what the cost of each query operation will be.

The following are the common types of file organizations used in indexing:

### Heap File

::: callout-note
## Heap Organization

Records are stored in **insertion order** — no sorting, no grouping. New rows are simply appended to the end of the file.

- **Access**: Full table scan required to find any record → $O(n)$
- **Best for**: Bulk loading data, write-heavy tables, full-table analytics
- **Index compatibility**: Any index type can be built *on top* of a heap file; the index itself provides the ordering
- **Limitation**: Without an index, every query reads every page

```
Heap File (unsorted):
┌──────────────────────────┐
│ Fatima | Laptop   | 1200 │  ← inserted first
│ Omar   | Headsets | 150  │
│ Ahmed  | Phone    | 500  │
│ Layla  | Watch    | 200  │  ← inserted last
└──────────────────────────┘
```
:::

### Sequential (Sorted) File

::: callout-note
## Sequential Organization

Records are stored **sorted by a key** (the ordering field). Finding a record by that key can use binary search.

- **Access**: Binary search on ordering key → $O(\log n)$ pages
- **Best for**: Range queries on the sort key (`WHERE salary BETWEEN 3000 AND 7000`)
- **Index compatibility**: A **sparse index** works perfectly — one index entry per page block
- **Limitation**: Insertions are expensive (must maintain sort order); only one sort order possible

```
Sequential File (sorted by Customer Name):
┌──────────────────────────┐
│ Ahmed  | Phone    | 500  │  ← A
│ Fatima | Laptop   | 1200 │  ← F
│ Kareem | Monitor  | 400  │  ← K
│ Omar   | Headsets | 150  │  ← O  ← binary search lands here
│ Youssef| Camera   | 700  │  ← Y
└──────────────────────────┘
```
:::

### Hash File

::: callout-note
## Hash Organization

Records are placed into **buckets** determined by a hash function $h(\text{key}) \mod B$, where $B$ is the number of buckets.

- **Access**: Equality lookup → $O(1)$ theoretical (one bucket access)
- **Best for**: Exact-match equality queries (`WHERE id = 42`)
- **Index compatibility**: Pairs naturally with a **hash index**
- **Limitation**: Range queries are **impossible** — hashing destroys sort order; overflow buckets degrade performance

```
Hash File (hash on Order ID, B = 3):
Bucket 0: │ Order 3 │ Order 6 │ Order 9  │
Bucket 1: │ Order 1 │ Order 4 │ Order 7  │ Order 10 │
Bucket 2: │ Order 2 │ Order 5 │ Order 8  │
```
:::

### Clustered File

::: callout-note
## Clustered Organization

Records are physically stored in the **same order as the primary index** (usually a B+ tree). The data file *is* the index leaf level.

- **Access**: Range queries read consecutive pages → minimizes I/O
- **Best for**: Range queries + sorted output on the clustering key
- **Index compatibility**: The table can have **only one** clustered index (one physical sort order)
- **MySQL InnoDB**: Every table is always a clustered B+ tree ordered by the primary key

```
Clustered File (clustered on Customer Name):
B+ Tree leaf pages:
Page 1: │ Ahmed, Phone, $500 │ Ahmed, Tablet, $300 │
Page 2: │ Fatima, Laptop, $1200 │ Fatima, Keyboard, $100 │
Page 3: │ Kareem, Monitor, $400 │ Layla, Watch, $200 │
Page 4: │ Omar, Headsets, $150 │ Omar, Charger, $50 │
```
:::

### Summary: File Organizations at a Glance

| Organization | Physical Order | Equality | Range Query | Insert Cost | Index Type |
|---|---|---|---|---|---|
| **Heap** | Insertion order | Scan $O(n)$ | Scan $O(n)$ | $O(1)$ — append | Any (index provides order) |
| **Sequential** | Sorted by key | Binary search $O(\log n)$ | Efficient on sort key | $O(n)$ — shift rows | Sparse index ideal |
| **Hash** | By `h(key)` | $O(1)$ | Not supported | $O(1)$ avg | Hash index |
| **Clustered** | Matches B+ tree | $O(\log n)$ | Excellent — consecutive pages | $O(\log n)$ + splits | One clustered B+ tree |

### Solved Example — Choosing a File Organization

::: callout-note
## 📝 Solved Example

**Problem:** A hospital `Patients` table stores 200,000 records. The following query patterns are observed:

| Query | Frequency |
|-------|----------|
| `WHERE patient_id = 'P00512'` | Very high (lookup by PK) |
| `WHERE age BETWEEN 30 AND 50` | High (age-range reports) |
| `WHERE department = 'Cardiology'` | High (department reports) |
| Bulk insert of 10,000 new admission records | Daily |

Recommend a file organization and justify your choice for each query.


**Solution:**

| Query | Recommended Organization | Justification |
|-------|--------------------------|---------------|
| Equality on `patient_id` | **Clustered** (B+ tree on `patient_id`) | $O(\log n)$ — primary key lookup; InnoDB auto-clusters on PK |
| Range on `age` | **Sequential** sorted by age, or secondary B+ tree index | Range scan is $O(\log n + k)$ with sorted file or B+ tree |
| Filter by `department` | **Secondary B+ tree index** on `department` | Unclustered index; if low-cardinality consider bitmap index |
| Bulk daily inserts | **Heap file** append for staging | $O(1)$ insert; batch-load into main table after admission |

::: callout-tip
In MySQL InnoDB, the table is always physically a **clustered B+ tree on the primary key**. All other access patterns are served by **secondary unclustered indexes**.
:::
:::

## Index Concepts

An **index** is an auxiliary data structure that maps **search key → record location (RID)**.
It is separate from the data file and maintained automatically on INSERT/UPDATE/DELETE.

### Index Entry Structure: Key → Value

Every entry in an index is a **key–value pair**:

| Component | What it holds |
|-----------|--------------|
| **Key** (search key) | A copy of the indexed column(s) value — e.g., `"Charlie"`, `42`, `"2024-01-15"` |
| **Value** (data reference) | A pointer to the actual row(s) in the main table — the **Record ID (RID)** = `(page_id, slot_id)` |

::: callout-note
## What the index actually stores

- **Copies of selected column values** (the search key) — not the full row
- **Pointers to the actual data rows** in the main table (RIDs), so the DBMS can fetch the full record when needed
- The structure stays **sorted** (B+ tree) or **hashed**, allowing fast lookups without scanning the entire table

This is why adding an index trades a little extra storage and write overhead for dramatically faster reads.
:::

::: callout-note
## 📝 Solved Example

**Problem:** The `Employee` table below is stored as a heap file across 3 pages. Build a **dense index** on the `Salary` column and a **sparse index** on the same column (assume 2 records/page).

| RID | Emp_id | Name | Salary | Dept |
|-----|--------|------|--------|------|
| (p1,s1) | E01 | Ahmed | 55,000 | IT |

| (p3,s2) | E06 | Kareem | 48,000 | HR |

## Types of Indexing Methods

Indexes are classified along three independent dimensions: **density**, **clustering**, and **key type**. Understanding these helps you choose the right index for each query pattern.

### Dense vs. Sparse Index

::: {.panel-tabset}

## Dense Index

A **dense index** has **one index entry for every record** in the data file.

- Works on any file organization (heap or sorted)
- Faster lookup — every record has a direct pointer
- Higher storage cost — index grows with the data

```
Data File          Dense Index
───────────        ────────────────────
Ahmed  | p1,s1  ←  Ahmed  → (p1,s1)
Fatima | p1,s2  ←  Fatima → (p1,s2)
Kareem | p2,s1  ←  Kareem → (p2,s1)
Omar   | p2,s2  ←  Omar   → (p2,s2)
```

## Sparse Index

A **sparse index** has **one index entry per page** (data block), not per record.

- Requires the data file to be **sorted** on the index key
- Much smaller index — fits in fewer pages
- Lookup: find the correct page via index, then scan within the page

```
Data File (sorted)   Sparse Index
──────────────────   ─────────────────
Page 1: Ahmed        Ahmed  → page 1
        Fatima       Kareem → page 2
Page 2: Kareem       Omar   → page 3
        Layla
Page 3: Omar
        Youssef
```

:::

::: callout-note
B+ trees in practice use a **hybrid** approach: sparse at internal levels (routing keys only), dense at the leaf level (one pointer per record).
:::

### Clustered vs. Unclustered Index

::: callout-important
## Clustered Index

The **physical order of data rows matches the index order**. Reading a range of index entries also reads consecutive pages.

- A table can have **only one** clustered index
- In **MySQL InnoDB**, the primary key is always the clustered index
- Secondary indexes store the primary key as their RID — one extra lookup per row ("index dive")

## Unclustered Index

The index order **does not match** the data order. Each index pointer may point to a different page.

- Many unclustered indexes allowed per table
- Range queries may cause one page I/O per row — expensive at scale
:::

| | Clustered | Unclustered |
|--|----------|------------|
| Range query ($k$ rows) | ~$k$ / records_per_page pages | Up to $k$ separate pages |
| Equality query | ~height pages | ~height pages |
| Build cost | High (file must be sorted) | Lower |
| Count per table | **Only one** | Many allowed |

### Primary vs. Secondary Index

| Type | Defined on | Key property |
|------|-----------|-------------|
| **Primary index** | The **ordering key** of a sequential/clustered file | One entry per distinct key value; non-duplicate |
| **Secondary index** | Any non-ordering attribute | Can have duplicate keys; always unclustered unless it matches the physical order |

::: callout-tip
A **secondary index** is the workhorse of OLTP systems — it allows fast lookup on any column (`email`, `phone`, `status`) without reorganizing the data file.
:::

### Solved Example — Clustered vs. Unclustered I/O Cost

::: callout-note
## 📝 Solved Example

**Problem:** An `Employee` table has 40,000 records stored across 2,000 pages (20 records/page). Department 4 (`Dno = 4`) has 4,000 employees.

- In the **clustered** case: all Dno=4 employees occupy consecutive pages.
- In the **unclustered** case: the 4,000 employees are randomly scattered (worst case: one per page).
- B+ tree height $h = 3$ for both indexes.

Compute the I/O cost for:
`SELECT * FROM Employee WHERE Dno = 4`


**Solution:**

**Clustered B+ tree index on Dno:**
$$\text{Pages for Dno=4} = \left\lceil \frac{4{,}000}{20} \right\rceil = 200 \text{ pages}$$
$$\text{Total I/O} = h + \text{data pages} = 3 + 200 = \mathbf{203} \text{ page reads}$$

**Unclustered B+ tree index on Dno:**
$$\text{Worst case: each matching record on a different page}$$
$$\text{Total I/O} = h + 4{,}000 = 3 + 4{,}000 = \mathbf{4{,}003} \text{ page reads}$$

| Index Type | I/O Cost | Notes |
|------------|----------|-------|
| Clustered | 203 reads | Sequential pages — disk-friendly |
| Unclustered | up to 4,003 reads | Random I/O — 20× more expensive |
| Full scan (no index) | 2,000 reads | Cheaper than unclustered for large selectivity! |

::: callout-important
When selectivity is high (many matching rows), the **optimizer may choose a full scan over an unclustered index** because random I/O becomes more expensive than sequential I/O.
:::
:::

## B-Tree and B+ Tree Index

Both B-Tree and B+ Tree are **self-balancing tree structures** used to keep data sorted and allow searches, insertions, and deletions in $O(\log n)$ time. They are the foundation of indexing in virtually every major RDBMS.

### B-Tree vs. B+ Tree: Key Differences

| Feature | B-Tree | B+ Tree |
|---|---|---|
| Data pointers | In **all nodes** (internal + leaf) | **Leaf nodes only** |
| Internal nodes | Store keys **and** data records | Store keys only (routing) |
| Leaf nodes | Not linked | Linked as a **doubly-linked list** |
| Range queries | Slower — may visit internal nodes | Fast — scan leaf chain sequentially |
| Space efficiency | Lower (data in every node) | Higher (internal nodes hold more keys → larger fan-out) |
| Used in practice | Rare (mostly theoretical) | **MySQL, PostgreSQL, Oracle, SQL Server** |

::: callout-note
## Why B+ Tree Won

Because internal nodes in a B+ Tree store **only keys** (no data), each internal node can hold far more keys — increasing the **fan-out** and reducing the tree height. A B+ Tree with order $d = 100$ over 100 million records has only **4 levels**. Range scans are also trivial: follow the leaf chain without backtracking through the tree.
:::

### B+ Tree Structure

- **Balanced**: all leaf nodes at the same depth $h$; guarantees $O(\log n)$ operations
- **Order $d$**: every internal node except the root holds between $d$ and $2d$ search keys
- **All data pointers in leaves**: internal nodes hold only keys for routing
- **Leaf chain**: leaf nodes are linked in a doubly-linked list for sequential range scans

### Cost Analysis

| Operation | I/O Cost | Formula |
|-----------|---------|---------|
| Equality search | $h$ page reads | $h = \lceil \log_d n \rceil$ |
| Range scan ($k$ results) | $h + \lceil k / f \rceil$ | $f$ = records per leaf page |
| Insert | $h + $ splits | Amortised $O(1)$ splits |
| Delete | $h + $ merges | Rare in practice |

**Example**: order $d = 100$, $n = 10^8$ records → $h = \lceil \log_{100} 10^8 \rceil = 4$ levels.
Four page reads to find any record in a 100-million-row table.

### Solved Example — B+ Tree Height and Search Cost

::: callout-note
## 📝 Solved Example

**Problem:** A `Transactions` table has 50 million records. A B+ tree index of order $d = 200$ is built on the `TransactionDate` column. Each leaf page holds 200 records.

**(a)** Calculate the tree height $h$.
**(b)** What is the I/O cost for an equality query (find transactions on a specific date, 5 matching records)?
**(c)** What is the I/O cost for a range query returning 10,000 transactions?
**(d)** How does this compare to a full table scan (20 records/page)?


**Solution:**

**(a)** Tree height:
$$h = \left\lceil \log_{2d}\, n \right\rceil = \left\lceil \log_{400}\, 50{,}000{,}000 \right\rceil = \left\lceil \frac{\log 50{,}000{,}000}{\log 400} \right\rceil = \left\lceil \frac{7.699}{2.602} \right\rceil = \lceil 2.96 \rceil = \mathbf{3 \text{ levels}}$$

**(b)** Equality search (5 rows on 1–2 leaf pages):
$$\text{I/O} = h + \text{leaf pages} = 3 + 1 = \mathbf{4 \text{ page reads}}$$

**(c)** Range scan (10,000 rows, 200 rows/leaf page):
$$\text{Leaf pages} = \left\lceil \frac{10{,}000}{200} \right\rceil = 50$$
$$\text{I/O} = h + 50 = 3 + 50 = \mathbf{53 \text{ page reads}}$$

**(d)** Full table scan:
$$\text{Pages} = \left\lceil \frac{50{,}000{,}000}{20} \right\rceil = 2{,}500{,}000 \text{ page reads}$$

| Method | I/O reads | Relative cost |
|--------|-----------|---------------|
| Equality + B+ tree | 4 | 1× |
| Range (10K rows) + B+ tree | 53 | 13× |
| Full table scan | 2,500,000 | 625,000× |
:::

## Hash Indexes

A **hash index** applies a hash function $h(k)$ to map a key to a **bucket** where matching records are stored.

```{mermaid}
%%| eval: true
%%| echo: false
flowchart LR
    k["Search Key k"]
    h["h(k) = k mod B"]
    b0["Bucket 0"]
    b1["Bucket 1"]
    b2["Bucket 2"]
    bN["Bucket B"]
    k --> h
    h -->|"h=0"| b0
    h -->|"h=1"| b1
    h -->|"h=2"| b2
    h -->|"..."| bN
```

| Characteristic | Value |
|---------------|-------|
| Equality search | O(1) theoretical |
| Range query | **Impossible** — hashing destroys order |
| Overflow | Buckets chain when full |

### Extendible Hashing

Uses a **global depth** and a **directory**. When a bucket overflows:
1. Split only the full bucket (not all buckets)
2. Double the directory only when all buckets at that depth are full

Hash indexes are available as `USING HASH` in PostgreSQL and as `MEMORY` storage engine indexes in MySQL.

### Solved Example — Hash Index Lookup and Its Limits

::: callout-note
## 📝 Solved Example

**Problem:** A hash index is built on `Employee.Ssn` using $h(k) = k \mod 7$ (7 buckets, numbered 0–6).

Employee SSNs: 123456789, 234567891, 345678902, 456789013, 567890124, 678901235, 789012346

**(a)** Assign each SSN to its bucket.
**(b)** Evaluate which of the following queries benefit from this hash index:

- Q1: `WHERE Ssn = 456789013`
- Q2: `WHERE Ssn BETWEEN 300000000 AND 500000000`
- Q3: `WHERE Ssn != 123456789`


**Solution:**

**(a)** Bucket assignments:

| SSN | $k \mod 7$ | Bucket |
|-----|-----------|--------|
| 123456789 | 123456789 mod 7 = **5** | Bucket 5 |
| 234567891 | 234567891 mod 7 = **0** | Bucket 0 |
| 345678902 | 345678902 mod 7 = **2** | Bucket 2 |
| 456789013 | 456789013 mod 7 = **4** | Bucket 4 |
| 567890124 | 567890124 mod 7 = **6** | Bucket 6 |
| 678901235 | 678901235 mod 7 = **1** | Bucket 1 |
| 789012346 | 789012346 mod 7 = **3** | Bucket 3 |

**(b)** Query analysis:

| Query | Uses hash index? | Reason |
|-------|-----------------|--------|
| Q1: `Ssn = 456789013` | ✅ **Yes** | Compute $456789013 \mod 7 = 4$, go directly to Bucket 4. O(1). |
| Q2: `Ssn BETWEEN ...` | ❌ **No** | Hashing destroys sort order — all 7 buckets must be scanned. |
| Q3: `Ssn != 123456789` | ❌ **No** | Negation requires checking all records not in Bucket 5 — full scan. |

## Bitmap Indexes

A **bitmap index** stores, for each distinct value $v$ of the indexed column, a **bit vector** of length $N$ (one bit per row), where bit $i = 1$ iff row $i$ has value $v$.

### Example

Table `Employee` with 8 rows and column `Gender`:

| Row | Ssn | Gender |
|-----|-----|-----|
| 1 | 123 | M |
| 2 | 333 | M |
| 3 | 999 | F |
| 4 | 987 | M |
| 5 | 666 | F |
| 6 | 453 | F |
| 7 | 888 | F |
| 8 | 963 | M |

Bitmap index on `Gender`:

| Value | Bit vector |
|-------|-----------|
| M | `1 1 0 1 0 0 0 1` |
| F | `0 0 1 0 1 1 1 0` |

### Bitwise Operations for Multi-Predicate Queries

```
Query: SELECT * FROM Employee WHERE Gender = 'F' AND Dno = 5
```

| Bitmap | Vector |
|--------|-------|
| `Gender = 'F'` | `0 0 1 0 1 1 1 0` |
| `Dno = 5` | `1 0 1 0 1 0 1 0` |
| **AND result** | `0 0 1 0 1 0 1 0` |

Rows 3, 5, and 7 satisfy both conditions — determined by **bitwise AND** in a single CPU operation across the entire table.

### When to Use Bitmap Indexes

::: callout-tip
Bitmap indexes are ideal for:

- **Low-cardinality columns**: Gender, Status, Region (few distinct values → compact bitmaps)
- **Analytical / OLAP queries** with many AND/OR column predicates
- **Data warehouse star-schema** dimension columns (InnoDB does not support bitmap indexes natively — they are a first-class citizen of Oracle and PostgreSQL with specialized extensions)

Avoid bitmap indexes on:
- **High-cardinality columns** (every value different → one bit vector per row = huge overhead)
- **OLTP tables with frequent writes** — bit vectors must be updated on every INSERT/UPDATE/DELETE
:::

### Oracle Bitmap Index

```sql
-- Oracle natively supports bitmap indexes
CREATE BITMAP INDEX idx_emp_sex ON Employee(Gender);
CREATE BITMAP INDEX idx_emp_dno ON Employee(Dno);

-- Query: optimizer combines bitmaps with bitwise AND/OR automatically
SELECT * FROM Employee WHERE Gender = 'F' AND Dno = 5;
```

PostgreSQL does not have a native `CREATE BITMAP INDEX`, but the query planner performs **bitmap index scans** by combining multiple B+ tree indexes with `BitmapAnd`/`BitmapOr` operations internally.

### Solved Example — Bitmap Index Multi-Predicate Query

::: callout-note
## 📝 Solved Example

**Problem:** A `Sales` table has 8 rows with columns `Region` and `Year`:

| Row | Region | Year |
|-----|--------|------|
| 1 | North | 2024 |
| 2 | South | 2023 |
| 3 | North | 2023 |

**Solution:**

**Step 1 — Build bitmap vectors:**

## Index Selection Guidelines

### When to Create an Index

| Create index when… | Avoid when… |
|-------------------|------------|
| Column frequent in `WHERE` predicates | Table has fewer than a few thousand rows |
| Column used in `JOIN … ON` condition | Column has very low cardinality (boolean, status with 2 values) — consider bitmap |
| Column in `ORDER BY` or `GROUP BY` | Table is write-heavy (INSERT/UPDATE/DELETE) — index maintenance overhead |
| Foreign key column (speeds up deletes of parent) | Column almost never queried alone |
| Covering index candidate (all SELECT cols in index) | Index is redundant with another existing index |

### Composite (Multi-Column) Index

::: {.panel-tabset}

## MySQL

```sql
-- Index on (Dno, Salary) — useful for filtering by dept and sorting by salary
CREATE INDEX idx_emp_dno_sal ON Employee(Dno, Salary);

-- A covering index: includes all columns needed by the query (avoids table lookup)
CREATE INDEX idx_emp_cover ON Employee(Dno, Salary, Fname, Lname);

-- Verify index usage
EXPLAIN SELECT Fname, Lname, Salary FROM Employee WHERE Dno = 5 ORDER BY Salary DESC;
```

## PostgreSQL

```sql
CREATE INDEX idx_emp_dno_sal ON Employee(Dno, Salary);

-- Partial index: only index rows matching a condition (smaller, faster for sparse predicates)
CREATE INDEX idx_emp_mgr ON Employee(Super_ssn) WHERE Super_ssn IS NOT NULL;

-- Functional index (index on expression)
CREATE INDEX idx_emp_lower_lname ON Employee(LOWER(Lname));

-- Verify
EXPLAIN ANALYZE SELECT Fname, Lname, Salary FROM Employee WHERE Dno = 5 ORDER BY Salary DESC;
```

::: callout-important
## Leftmost Prefix Rule for Composite Indexes

A composite index on `(A, B, C)` is usable for:

| Query predicate | Index used? |
|----------------|------------|
| `WHERE A = ?` | ✓ |
| `WHERE A = ? AND B = ?` | ✓ |
| `WHERE A = ? AND B = ? AND C = ?` | ✓ |
| `WHERE B = ?` | ✗ (leftmost column skipped) |
| `WHERE C = ?` | ✗ |
| `WHERE A = ? AND C = ?` | Partial ✓ for A only |
| `ORDER BY A, B` | ✓ (avoids sort step) |
:::

### Solved Example — Index Design for a Real Table

::: callout-note
## 📝 Solved Example

**Problem:** An e-commerce platform has an `Orders` table:

```sql
CREATE TABLE Orders (
    OrderId    INT         PRIMARY KEY,
    CustomerId VARCHAR(20),
    ProductId  VARCHAR(20),
    Status     CHAR(1),          -- 'P'=Pending, 'S'=Shipped, 'D'=Delivered, 'C'=Cancelled
    OrderDate  DATE,
    Amount     DECIMAL(10,2)
);
```

The following queries run frequently:

| Query | Description |
|-------|-------------|
| Q1 | `WHERE CustomerId = 'C0412'` | Lookup customer orders |
| Q2 | `WHERE OrderDate BETWEEN '2024-01-01' AND '2024-12-31'` | Annual report |
| Q3 | `SELECT ProductId, SUM(Amount) WHERE Status = 'D' GROUP BY ProductId` | Revenue by product |
| Q4 | `WHERE CustomerId = 'C0412' AND OrderDate > '2024-06-01'` | Recent orders |

The table has **10 million rows**. `Status` has only 4 distinct values. Design an indexing strategy.


**Solution:**

| Index | Definition | Serves | Justification |
|-------|-----------|--------|---------------|
| Clustered (auto) | `PRIMARY KEY (OrderId)` | PK lookups | InnoDB clusters on PK |
| Secondary B+ tree | `(CustomerId)` | Q1 | High-cardinality, frequent equality |
| Secondary B+ tree | `(OrderDate)` | Q2 | Range query on date |
| Covering index | `(CustomerId, OrderDate)` | Q4 | Leftmost prefix covers both predicates; replaces individual indexes for Q1+Q4 |
| B+ tree (or Bitmap) | `(Status)` | Q3 | Low-cardinality (4 values); Oracle: BITMAP; MySQL: B+ tree |
| Composite covering | `(Status, ProductId, Amount)` | Q3 | Covers the entire query — no table lookup needed |

```sql
-- MySQL / PostgreSQL
CREATE INDEX idx_orders_cust_date ON Orders(CustomerId, OrderDate);
CREATE INDEX idx_orders_status_prod ON Orders(Status, ProductId, Amount);

-- Oracle (bitmap for Status)
CREATE BITMAP INDEX idx_orders_status ON Orders(Status);
CREATE INDEX idx_orders_prod_amount ON Orders(ProductId, Amount);

-- Verify with EXPLAIN
EXPLAIN SELECT ProductId, SUM(Amount) FROM Orders WHERE Status = 'D' GROUP BY ProductId;
```

::: callout-caution
**Avoid** creating separate indexes on `CustomerId` and `OrderDate` when a composite `(CustomerId, OrderDate)` already covers both — two indexes = 2× write overhead for zero additional read benefit.
:::
:::

## Chapter Summary

::: callout-important
## Key Takeaways — Chapter 10

1. **All disk I/O transfers pages** (4–16 KB). The buffer manager caches pages; the cost metric is page reads.

2. **File organizations**: heap (insertion order), sequential (sorted), hash, clustered.
   MySQL InnoDB stores data in the clustered B+ tree (primary key order).

3. **Dense vs sparse**: dense index has one entry per record; sparse index has one entry per page (requires sorted file).

4. **B+ tree**: balanced, fan-out $2d$, height $h \approx \log_d n$.
   All leaves linked for range scans. Supports equality, range, ORDER BY, and GROUP BY efficiently.
   With $d = 100$ and $10^8$ records: only **4 page reads** to find any record.

5. **Hash index**: O(1) equality; completely useless for range queries.

6. **Bitmap index**: per-distinct-value bit vectors; bitwise AND/OR answering multi-predicate analytical queries at CPU speed. Best for low-cardinality columns in OLAP.

7. **Composite indexes**: leftmost prefix rule determines which predicates the index covers.
   A covering index includes all columns a query needs — eliminates all table lookups.

8. Use `EXPLAIN` / `EXPLAIN ANALYZE` to verify that the optimizer selects the intended index.
:::
