9.1 The Problem – A Single Table Approach

Imagine a university keeps all student enrollment data in a single table named Enrollment:

StudentID StudentName CourseID CourseTitle Instructor Grade
101 Ahmed CS101 Intro to CS Dr. Sameer A
101 Ahmed MATH201 Calculus II Dr. Ibrahem B+
102 Sami CS101 Intro to CS Dr. Layla A-
102 Sami PHY301 Quantum Physics Dr. Amani C

This looks simple — but it contains serious problems known as anomalies.

9.2 Anomalies in Unnormalized Tables

9.2.1 (a) Insertion Anomaly

Problem: Cannot insert certain data without other unrelated data.

Suppose a new course CS202 – Data Structures is added, but no student has enrolled yet. You cannot insert CourseID = CS202 and CourseTitle = Data Structures unless you also have a StudentID. The course information depends on a student being enrolled.

StudentID StudentName CourseID CourseTitle Instructor Grade
101 Ahmed CS101 Intro to CS Dr. Layla A
101 Ahmed MATH201 Calculus II Dr. Ibrahem B+
102 Sami CS101 Intro to CS Dr. Layla A-
102 Sami PHY301 Quantum Physics Dr. Amani C
Null Null CS202 Data Structures Null Null

9.2.2 (b) Deletion Anomaly

Problem: Deleting data unintentionally removes other important data.

If Ahmed drops MATH201, and he was the only student in that course, deleting his record also deletes the course info (MATH201, Calculus II, Dr. Ibrahem).

StudentID StudentName CourseID CourseTitle Instructor Grade
101 Ahmed CS101 Intro to CS Dr. Layla A
101 Ahmed MATH201 Calculus II Dr. Ibrahem B+
102 Sami CS101 Intro to CS Dr. Layla A-
102 Sami PHY301 Quantum Physics Dr. Amani C

9.2.3 (c) Update Anomaly

Problem: Redundant data leads to inconsistencies during updates.

Dr. Layla teaches CS101. Her name appears in every row where CS101 is offered. If Dr. Layla changes her name (e.g., to Prof. Layla), you must update every row with CS101. If you miss one row, data becomes inconsistent.

StudentID StudentName CourseID CourseTitle Instructor Grade
101 Ahmed CS101 Intro to CS Prof. Layla A
101 Ahmed MATH201 Calculus II Dr. Ibrahem B+
102 Sami CS101 Intro to CS Dr. Layla ← inconsistent! A-
102 Sami PHY301 Quantum Physics Dr. Amani C

Root cause: a single row stores facts about three separate entities — students, courses, and enrollments — all mixed together.

9.3 Solution: Normalization

Normalization is the process of decomposing a table into smaller, well-structured tables to:

  • Eliminate redundancy — the same data isn’t stored multiple times unnecessarily
  • Avoid anomalies — relationships between tables are clear and logical
  • Ensure data integrity — queries run faster and are easier to maintain

We split the Enrollment table into three tables:

Students

StudentID StudentName
101 Ahmed
102 Sami

Courses

CourseID CourseTitle Instructor
CS101 Intro to CS Dr. Layla
MATH201 Calculus II Dr. Ibrahem
PHY301 Quantum Physics Dr. Amani

Enrollments

StudentID CourseID Grade
101 CS101 A
101 MATH201 B+
102 CS101 A-
102 PHY301 C

Now each anomaly disappears:

  • Adding a new course? Just insert into Courses — no student needed.
  • A student drops a course? Delete only from Enrollments — course data stays intact.
  • Instructor name changes? Update one row in Courses — done.

9.4 Functional Dependencies

9.4.1 The Bridge Between Business Rules and Database Design

Before we can normalize, we need a precise language for describing what determines what in a relation. That language is functional dependencies (FDs).

Think of it like a deterministic mathematical function:

y = f(x) \quad \Longrightarrow \quad \text{knowing } x \text{ always gives you exactly one } y

The database equivalent is written X \to Y and reads:

“For every valid instance of X, there is a unique value of Y in the table.”

In other words, if two rows have the same X value, they must have the same Y value — no exceptions.

Example: A company assigns each employee a unique EmpNo.

SSN \to Name

  • Meaning: if you give me the value of SSN, I can tell you the name of that employee.
  • The expression SSN \to Name is read as “SSN defines Name” or “SSN implies Name.”
  • But Name \to SSN? No — it would be inconsistent if two different employees happened to share the same name; their SSNs would differ, so Name cannot determine SSN.
Important💡 FDs come from domain knowledge — not from data!

FDs are a characteristic of the relation schema itself. They describe rules that must hold for all possible data in that schema — not just today’s snapshot.

  • ❌ Don’t assume an FD just because it happens to hold in the current rows.
  • ⚠️ An FD must hold for every valid state the relation could ever be in.

9.4.2 Types of Functional Dependencies

Term Meaning
Trivial FD X \to Y where Y \subseteq X (e.g., \{A,B\} \to A) — always true, carries no information
Non-trivial FD Y \not\subseteq X — the interesting kind
Full FD X \to Y and no proper subset of X also determines Y
Partial FD A proper subset of X already determines Y — redundancy red flag for 2NF
Transitive FD X \to Y \to Z where Y is not a key — redundancy red flag for 3NF

9.4.3 Discovering FDs from Stakeholders

FDs are discovered by asking domain experts — the people who own the business rules.

Example — you ask the University Registrar:

Question Answer FD Captured
“Is StudentID unique?” “Yes!” StudentID \to StudentName
“Can CS301 have two titles?” “No! Course title is fixed.” CourseID \to CourseTitle
“Can one course have multiple instructors?” “Not in the same term.” (CourseID, Term) \to Instructor
“What determines a student’s grade?” “Their performance in a specific course.” (StudentID, CourseID) \to Grade

✅ These business rules become functional dependencies!

9.4.4 FD Validation

An FD is valid (holds) when: for every pair of rows in the table that share the same LHS value, they also share the same RHS value. Formally:

X \to Y holds iff for every two tuples t_1, t_2: if t_1[X] = t_2[X] then t_1[Y] = t_2[Y].

NoteExample: FD Validation

Consider the relation R(A, B, C, D) with the following instance:

A B C D
1 1 2 3
1 2 2 3
1 3 2 3
2 4 5 6
5 6 7 8

Which of the following FDs are satisfied by this relation?

  1. A \to B   (b) A \to CD   (c) AB \to CD   (d) C \to D   (e) B \to A

  2. BD \to AC   (g) AD \to BC   (h) D \to B   (i) D \to C   (j) C \to A

Solution

(a) A \to B — ❌ Does not hold. For A = 1 there are three different B values: 1, 2, and 3.

(b) A \to CD — ✅ Holds. For every A value there is exactly one (C, D) pair: A=1 \Rightarrow (2,3), A=2 \Rightarrow (5,6), A=5 \Rightarrow (7,8).

(c) AB \to CD — ✅ Holds. Every (A,B) combination is unique (appears only once), so each maps to exactly one (C,D).

(d) C \to D — ✅ Holds. C=2 \Rightarrow D=3, C=5 \Rightarrow D=6, C=7 \Rightarrow D=8.

(e) B \to A — ✅ Holds. Every B value is unique in this instance, so it maps to a single A.

(f) BD \to AC — ✅ Holds. Each (B,D) combination appears at most once.

(g) AD \to BC — ❌ Does not hold. For (A,D) = (1,3) there are three (B,C) pairs: (1,2), (2,2), (3,2).

(h) D \to B — ❌ Does not hold. For D = 3 there are three B values: 1, 2, and 3.

(i) D \to C — ✅ Holds. D=3 \Rightarrow C=2, D=6 \Rightarrow C=5, D=8 \Rightarrow C=7.

(j) C \to A — ✅ Holds in this instance. C=2 \Rightarrow A=1, C=5 \Rightarrow A=2, C=7 \Rightarrow A=5. Each C value maps to a unique A.

⚠️ Note: (e) and (j) hold only in this particular instance. Without a domain rule confirming them, they cannot be declared FDs of the schema.

9.5 Keys and Functional Dependencies

9.5.1 Review of Keys

A key is a set of attributes that uniquely identifies a tuple (row) in a relation (table).

Key Type Definition
Super Key Any set of attributes that uniquely identifies a tuple. May contain extra attributes that are not necessary for uniqueness.
Candidate Key A minimal super key — the smallest set of attributes that can uniquely identify a tuple. A table can have multiple candidate keys.
Primary Key The candidate key chosen by the database designer to be the official unique identifier for the table.

9.5.2 Deriving Keys from FDs

The procedure moves from super keys down to candidate keys:

  1. Start with a set of attributes X.
  2. Compute X^+ (the closure of X under the FD set F).
  3. If X^+ includes all attributes in the relation, then X is a super key.
  4. If X is minimal (no proper subset of X is also a super key), then X is a candidate key.
Note

Why minimality matters: If a super key is not minimal, it contains extra attributes that are not required for uniqueness — and therefore it cannot be a candidate key.

NoteExample 1: Single Candidate Key

Consider R(A, B, C, D) with the following functional dependencies:

  • A \to B
  • B \to C
  • C \to D

Find all super keys and candidate keys.

Solution

Step 1 — Find super keys by testing closures:

Set X X^+ Super key?
\{A\} \{A, B, C, D\} ✓
\{A, B\} \{A, B, C, D\} ✓
\{A, C\} \{A, B, C, D\} ✓
\{A, D\} \{A, B, C, D\} ✓
\{A, B, C\} \{A, B, C, D\} ✓
\{A, B, D\} \{A, B, C, D\} ✓
\{A, C, D\} \{A, B, C, D\} ✓
\{A, B, C, D\} \{A, B, C, D\} ✓
\{B\} \{B, C, D\} ✗
\{C\} \{C, D\} ✗
\{D\} \{D\} ✗

Step 2 — Check minimality:

  • \{A\} is minimal → ✅ Candidate key
  • \{A, B\} — contains \{A\} which is already a super key → ✗ not minimal
  • \{A, C\}, \{A, D\}, \{A,B,C\}, … — all contain \{A\} → ✗ not minimal

Result: The only candidate key is \{A\}.

NoteExample 2: Multiple Candidate Keys

Consider R(A, B, C, D) with the following functional dependencies:

  • A \to B
  • C \to D
  • A, C \to D
  • B, C \to A

Determine the candidate keys.

Solution

Compute closures of candidate LHS sets:

\{A, C\}^+: - Start: \{A, C\} - A \to B → add B: \{A, B, C\} - C \to D → add D: \{A, B, C, D\} = R ✓ → super key - Subsets: \{A\}^+ = \{A,B\}, \{C\}^+ = \{C,D\} — neither covers R → minimal - → ✅ Candidate key: \{A, C\}

\{B, C\}^+: - Start: \{B, C\} - B, C \to A → add A: \{A, B, C\} - C \to D → add D: \{A, B, C, D\} = R ✓ → super key - Subsets: \{B\}^+ = \{B\}, \{C\}^+ = \{C,D\} — neither covers R → minimal - → ✅ Candidate key: \{B, C\}

Result: Candidate keys are \{A, C\} and \{B, C\}.

NoteExample 3: Systematic Closure Method

Consider R(A, B, C, D) with:

BC \to A, \quad AD \to B, \quad CD \to B, \quad AC \to D

Find all candidate keys of R.

Solution

Compute the closure of each two-attribute combination:

LHS Derivation (\cdot)^+ Candidate Key?
(BC)^+ BC \to A → \{A,B,C\}; then AC \to D → \{A,B,C,D\} R ✅
(AD)^+ AD \to B → \{A,B,D\}; no further FDs apply \{A,B,D\} \ne R ✗
(CD)^+ CD \to B → \{B,C,D\}; then BC \to A → \{A,B,C,D\} R ✅
(AC)^+ AC \to D → \{A,C,D\}; then CD \to B → \{A,B,C,D\} R ✅

Result: Candidate keys are \{B,C\}, \{C,D\}, and \{A,C\}.

Note: \{A,D\}^+ = \{A,B,D\} — it cannot reach C, so it is not a super key.

9.6 Types of Functional Dependencies

9.6.1 1. Trivial Functional Dependency

A functional dependency X \to Y is trivial if Y \subseteq X — that is, Y is a subset of X.

Trivial FDs always hold and carry no useful information about the data.

Examples:

  • \{StudentID, StudentName\} \to StudentName — trivial, because StudentName is already in the LHS
  • \{A, B\} \to A — trivial
  • \{A, B\} \to \{A, B\} — trivial

9.6.2 2. Non-Trivial Functional Dependency

A functional dependency X \to Y is non-trivial if Y \not\subseteq X — at least one attribute on the RHS is not already on the LHS.

These are the meaningful FDs that capture real business rules.

Examples:

  • StudentID \to StudentName — non-trivial: StudentName is not part of StudentID
  • CourseID \to CourseTitle, Instructor — non-trivial
  • \{A, B\} \to C — non-trivial if C \notin \{A, B\}

9.6.3 3. Transitive Functional Dependency

If X \to Y and Y \to Z both hold in a relation, then X \to Z also holds. This is called a transitive dependency. For a transitive dependency to exist, there must be at least three attributes in the relation.

X \xrightarrow{\text{direct}} Y \xrightarrow{\text{direct}} Z \quad\Longrightarrow\quad X \xrightarrow{\text{transitive}} Z

Example:

In a student table: - StudentID \to DeptID (student belongs to a department) - DeptID \to DeptName (department has a name) - Therefore: StudentID \to DeptName — transitive, because DeptID is not a key

This is the red flag that 3NF eliminates.

9.6.4 4. Full Functional Dependency

A functional dependency X \to Y is full if removing any single attribute from X means the dependency no longer holds. Every attribute in X is necessary.

Example:

Consider an Enrollment table with composite key \{StudentID, CourseID\}:

  • \{StudentID, CourseID\} \to Grade — full, because:
    • StudentID \to Grade? ❌ No — the same student can get different grades in different courses
    • CourseID \to Grade? ❌ No — different students get different grades for the same course
    • Both attributes are required → full FD

9.6.5 5. Partial Functional Dependency

A functional dependency A \to B is partial if some attribute in A can determine B on its own, without needing the entire set A.

Partial dependencies only arise when the key is composite (more than one attribute).

Example:

Same Enrollment table with composite key \{StudentID, CourseID\}:

  • \{StudentID, CourseID\} \to StudentName — partial, because:
    • StudentID \to StudentName? ✅ Yes — student name depends only on the student, not the course
    • CourseID is irrelevant for determining StudentName
FD Type Why
\{StudentID, CourseID\} \to Grade Full Both attributes needed
\{StudentID, CourseID\} \to StudentName Partial Only StudentID needed
\{StudentID, CourseID\} \to CourseTitle Partial Only CourseID needed

Partial dependencies cause the redundancy that 2NF eliminates by decomposing the table.

9.7 Normalization

Normalization is the systematic approach of effectively designing a database so that it minimizes data redundancy and inconsistency. It is generally done through a series of steps called normal forms (NF).

Each normal form builds on the previous one — a relation in a higher NF automatically satisfies all lower NFs:

1NF \;\subset\; 2NF \;\subset\; 3NF \;\subset\; BCNF \;\subset\; 4NF \;\subset\; 5NF

Normal Form Key Requirement What it Eliminates
1NF All attribute values are atomic Multi-valued / repeating groups
2NF 1NF + no partial FDs on any candidate key Redundancy from partial dependencies
3NF 2NF + no transitive FDs (with prime-attr exception) Transitive dependencies via non-key attributes
BCNF Every FD determinant is a superkey All non-trivial FD-based redundancy
4NF BCNF + no non-trivial MVDs Multi-valued dependency redundancy
5NF 4NF + no non-trivial join dependencies Decomposition artifacts

9.7.1 First Normal Form (1NF)

Definition: A relation is in 1NF if:

  • Every attribute contains only atomic (single-valued, indivisible) values
  • There are no repeating groups or multi-valued attributes
  • There is a primary key that uniquely identifies each row
NoteExample: Violating 1NF

A student table stores multiple courses in one cell:

StudentNo StudentName Courses
S1 Ahmed DS, Algorithms
S2 Hussein Databases

Courses is not atomic — it holds multiple values in one cell. This violates 1NF.

Solution: Convert to 1NF

Split into separate rows so each cell holds one value:

StudentNo StudentName CourseNo CourseName
S1 Ahmed CS101 Data Structures
S1 Ahmed CS102 Algorithms
S2 Hussein CS301 Databases
  • Each cell now holds exactly one value ✅
  • Primary key: {StudentNo, CourseNo} uniquely identifies each row ✅

Note: StudentName is now repeated for Ahmed. This redundancy is addressed in 2NF.

9.7.2 Second Normal Form (2NF)

Definition: A relation is in 2NF if:

  • It is already in 1NF, AND
  • Every non-prime attribute is fully functionally dependent on every candidate key

2NF is only relevant when the primary key is composite. A relation with a single-attribute primary key is automatically in 2NF if it is in 1NF.

A partial dependency exists when a non-key attribute depends on only part of a composite key. 2NF eliminates all partial dependencies.

NoteExample: Violating 2NF

Using the 1NF table from above with composite key {StudentNo, CourseNo}:

StudentNo StudentName CourseNo CourseName InstructorNo Grade
S1 Ahmed CS101 Data Structures I1 A
S1 Ahmed CS102 Algorithms I2 B+
S2 Hussein CS301 Databases I3 A-

Partial dependencies present:

  • StudentNo \to StudentName — depends only on StudentNo, not CourseNo
  • CourseNo \to CourseName, InstructorNo — depends only on CourseNo, not StudentNo

Only \{StudentNo, CourseNo\} \to Grade is a full dependency.

Solution: Convert to 2NF

Decompose by moving each partial dependency to its own table:

Students (key: StudentNo)

StudentNo StudentName
S1 Ahmed
S2 Hussein

Courses (key: CourseNo)

CourseNo CourseName InstructorNo
CS101 Data Structures I1
CS102 Algorithms I2
CS301 Databases I3

Enrollments (key: {StudentNo, CourseNo})

StudentNo CourseNo Grade
S1 CS101 A
S1 CS102 B+
S2 CS301 A-

All non-key attributes now depend on the whole key of their table. ✅

9.7.3 Third Normal Form (3NF)

Definition: A relation is in 3NF if:

  • It is already in 2NF, AND
  • For every non-trivial FD X \to A: either X is a superkey, or A is a prime attribute

A transitive dependency exists when a non-key attribute determines another non-key attribute: Key \to Y \to Z where Y is not a key. 3NF eliminates these.

NoteExample: Violating 3NF

Suppose the Courses table from 2NF also stores instructor details:

CourseNo CourseName InstructorNo InstructorName InstructorLocation
CS101 Data Structures I1 Dr. Ali Building A
CS102 Algorithms I2 Dr. Sara Building B
CS301 Databases I1 Dr. Ali Building A

Transitive dependency:

CourseNo \to InstructorNo \to InstructorName, InstructorLocation

InstructorNo is not a candidate key of Courses, so InstructorName and InstructorLocation transitively depend on CourseNo.

Solution: Convert to 3NF

Move the transitive dependency to its own table:

Courses (key: CourseNo)

CourseNo CourseName InstructorNo
CS101 Data Structures I1
CS102 Algorithms I2
CS301 Databases I1

Instructors (key: InstructorNo)

InstructorNo InstructorName InstructorLocation
I1 Dr. Ali Building A
I2 Dr. Sara Building B

Now InstructorName and InstructorLocation depend directly on their key InstructorNo. ✅ Updating Dr. Ali’s location requires changing one row only.

9.7.4 Boyce-Codd Normal Form (BCNF)

Definition: A relation is in BCNF if:

  • It is already in 3NF, AND
  • For every non-trivial FD X \to Y: X must be a superkey

BCNF is stricter than 3NF — it removes the “prime attribute” exception. A relation can be in 3NF but not BCNF when there are multiple overlapping candidate keys.

NoteExample: 3NF but not BCNF 
Enrolment(Student, Course, Teacher)

FDs: - \{Student, Course\} \to Teacher — a student in a course has one teacher - Teacher \to Course — each teacher teaches exactly one course

Candidate keys: \{Student, Course\} and \{Student, Teacher\}

Check: Teacher \to Course — Teacher is not a superkey → BCNF violated

But Course is a prime attribute (part of candidate key \{Student, Course\}) → 3NF holds

Solution: Convert to BCNF

Decompose on the violating FD Teacher \to Course:

TeacherCourse (key: Teacher)

Teacher Course
Dr. Ali Databases
Dr. Sara Algorithms

StudentTeacher (key: {Student, Teacher})

Student Teacher
Ahmed Dr. Ali
Yaser Dr. Sara

Both tables are now in BCNF. ✅

Trade-off: the FD \{Student, Course\} \to Teacher can no longer be verified in a single table — it requires a join. This is the dependency-preservation cost of BCNF decomposition.

9.7.5 Worked Example: Full Normalization (1NF → 3NF)

The following example applies all three normal forms step by step to the university enrollment scenario.

Starting table — Enrollment with composite key {StudentID, CourseID}:

StudentID StudentName CourseID CourseTitle Instructor Grade
101 Ahmed CS101 Intro to CS Dr. Sameer A
101 Ahmed MATH201 Calculus II Dr. Ibrahem B+
102 Sami CS101 Intro to CS Dr. Layla A-
102 Sami PHY301 Quantum Physics Dr. Amani C

FDs:

StudentID  → StudentName
CourseID   → CourseTitle, Instructor
{StudentID, CourseID} → Grade

Step 1 — Is it in 1NF?

Every cell contains a single atomic value and there is a primary key. ✅ Already in 1NF.

Step 2 — Check for 2NF

The key is composite {StudentID, CourseID}. Check for partial dependencies:

FD Partial?
StudentID \to StudentName ✅ Partial — only StudentID needed
CourseID \to CourseTitle, Instructor ✅ Partial — only CourseID needed
\{StudentID, CourseID\} \to Grade ✗ Full — both needed

Not in 2NF. Decompose:

Students(StudentID PK, StudentName)
Courses(CourseID PK, CourseTitle, Instructor)
Enrollments(StudentID FK, CourseID FK, Grade)   -- PK = {StudentID, CourseID}

✅ Now in 2NF — no partial dependencies remain.

Step 3 — Check for 3NF

Check each table for transitive dependencies:

  • Students(StudentID, StudentName) — no transitive FD. ✅
  • Enrollments(StudentID, CourseID, Grade) — no transitive FD. ✅
  • Courses(CourseID, CourseTitle, Instructor) — does Instructor → CourseTitle? Only if each instructor teaches exactly one course. If that is a business rule, it is a transitive FD and must be decomposed further. Otherwise ✅ in 3NF as-is.

9.8 More Normalization Examples

9.8.1 Example 1 — Simple: Identify the Normal Form

NoteQuestion

Given the relation R(A, B, C, D, E) with F = \{AB \to CD,\ B \to C\}. Is R in 2NF? If not, convert it to 2NF.

Solution

Step 1 — Find the candidate key.

Attributes A, B, D, E do not appear on any RHS, so they must be part of every candidate key. \{A, B, D, E\}^+:

  • AB \to CD → add C, D: \{A,B,C,D,E\} = R ✓

Candidate key: \{A, B, D, E\}

Step 2 — Check for partial dependencies.

Non-prime attributes: C.

  • B \to C — B is a proper subset of the key \{A,B,D,E\} → partial dependency ✗

Conclusion: R is not in 2NF.

Step 3 — Decompose.

Move the partial dependency B \to C to its own relation:

  • R_1(B, C) — key: B
  • R_2(A, B, D, E) — key: \{A, B, D, E\}

Both R_1 and R_2 are in 2NF. ✅

9.8.2 Example 2 — Simple: 1NF → 2NF → 3NF (Library Database)

NoteQuestion

A library database stores borrowing records in a single table:

Borrow(\underline{MemberID},\ MemberName,\ \underline{BookID},\ BookTitle,\ Author,\ BorrowDate,\ ReturnDate)

FDs:

  • MemberID \to MemberName
  • BookID \to BookTitle,\ Author
  • \{MemberID, BookID\} \to BorrowDate,\ ReturnDate

Normalize to 3NF, showing each step.

Solution

1NF check: Every attribute is atomic and the table has a primary key \{MemberID, BookID\}. ✅

2NF check: Key is composite → check for partial dependencies:

FD Partial?
MemberID \to MemberName ✅ depends only on MemberID
BookID \to BookTitle, Author ✅ depends only on BookID
\{MemberID, BookID\} \to BorrowDate, ReturnDate ✗ full

Not in 2NF. Decompose:

Members(\underline{MemberID},\ MemberName) Books(\underline{BookID},\ BookTitle,\ Author) Borrowings(\underline{MemberID},\ \underline{BookID},\ BorrowDate,\ ReturnDate)

All three tables are now in 2NF. ✅

3NF check: Inspect each table for transitive dependencies:

  • Members — only MemberID \to MemberName, no transitive FD. ✅
  • Books — only BookID \to BookTitle, Author, no transitive FD. ✅
  • Borrowings — no non-key attributes determine other non-key attributes. ✅

Final 3NF schema:

Table Key Attributes
Members MemberID MemberName
Books BookID BookTitle,\ Author
Borrowings \{MemberID, BookID\} BorrowDate,\ ReturnDate

✅ All tables in 3NF.

NoteQuestion

An e-commerce company stores orders in a single table:

  • OrderID \to CustomerID,\ ProductID,\ Qty
  • CustomerID \to CustomerName,\ CustomerCity
  • ProductID \to ProductName,\ UnitPrice

Solution

Chain Transitive?
OrderID \to CustomerID \to CustomerName, CustomerCity ✅ CustomerID is not a key

9.9 Normal Form Summary

Normal Form Condition What it eliminates
1NF All attributes atomic Multi-valued / repeating groups
2NF 1NF + no partial FDs Redundancy from composite-key partial deps
3NF 2NF + no transitive FDs (with prime-attr exception) Transitive deps via non-key attributes
BCNF Every FD determinant is a superkey All non-trivial FD redundancy
4NF BCNF + no non-trivial MVDs Multi-valued dependency redundancy
5NF 4NF + no non-trivial join dependencies Decomposition artifacts
Important3NF vs BCNF Trade-off
Property 3NF BCNF
Lossless decomposition ✓ ✓
Dependency preservation ✓ (always) ✗ (may lose some FDs)
Eliminates all FD-based redundancy Partial Yes

Use BCNF when possible; fall back to 3NF when you must preserve a specific dependency.

9.10 BCNF Decomposition — A Case Where 3NF ≠ BCNF

The BCNF and 3NF distinction matters when there are multiple overlapping candidate keys.

Classic example:

Enrolment(Student, Course, Teacher)

FDs: - {Student, Course} → Teacher (a course has exactly one teacher per student) - Teacher → Course (a teacher teaches exactly one course)

Candidate keys: - {Student, Course} — covers all columns - {Student, Teacher} — covers all columns (because Teacher → Course)

Check for BCNF violations: - Teacher → Course: determinant Teacher is NOT a superkey → BCNF violated

Check for 3NF violations: - Teacher → Course: Course is a prime attribute (member of candidate key {Student, Course}) → 3NF satisfied (prime-attr exception)

So Enrolment is in 3NF but not in BCNF.

BCNF decomposition:

TeacherCourse(Teacher PK, Course)       -- FD: Teacher → Course
StudentTeacher(Student, Teacher)        -- PK: {Student, Teacher}

Trade-off: the FD {Student, Course} → Teacher can no longer be checked in a single table — it requires a join. That is the dependency-preservation loss inherent to BCNF decomposition.

9.11 Multivalued Dependencies and 4NF

A multivalued dependency (MVD) X \twoheadrightarrow Y holds when, for each value of X, the set of Y values is independent of the remaining attributes Z.

Example:

EmployeeSkillHobby(Ssn, Skill, Hobby)

An employee has a set of skills and a set of hobbies, and these are independent of each other. MVDs: Ssn ↠ Skill and Ssn ↠ Hobby.

This causes redundancy: each (Ssn, Skill) pair must be repeated for each Hobby.

Ssn Skill Hobby
111 Java Chess
111 Java Soccer
111 SQL Chess
111 SQL Soccer

4NF requires that every non-trivial MVD X \twoheadrightarrow Y has X as a superkey.

Fix:

EmployeeSkill(Ssn, Skill)
EmployeeHobby(Ssn, Hobby)

9.12 Canonical Cover (Minimal Cover)

The canonical cover F_c of an FD set F is an equivalent, minimal FD set:

  1. Every FD has a single attribute on the right side (decompose all compound RHS)
  2. No FD has a redundant attribute on the left side (check if dropping a LHS attribute leaves the FD derivable)
  3. No FD is redundant overall (check if removing the whole FD leaves it derivable from the rest)

Why compute F_c? The 3NF synthesis algorithm uses F_c to generate the minimal, dependency-preserving, lossless schema.

9.13 Dependency Preservation

A decomposition \{R_1, R_2, \ldots, R_k\} of R is dependency-preserving iff every FD in F^+ can be verified in at least one R_i without performing a join:

\left(\bigcup_{i=1}^{k} F_i\right)^+ = F^+

where F_i = projection of F onto R_i.

BCNF decompositions may not be dependency-preserving (as shown in §9.7). The 3NF synthesis algorithm always produces a lossless, dependency-preserving decomposition.

9.14 Chapter Summary

ImportantKey Takeaways — Chapter 9

  1. Update anomalies (insertion, deletion, modification) arise whenever a table stores facts about multiple unrelated entities. Normalization eliminates the root cause.

  2. A functional dependency X \to Y means knowing X always determines Y. Key types: full (depends on whole key), partial (depends on subset), transitive (X \to Y \to Z).

  3. Armstrong’s Axioms (Reflexivity, Augmentation, Transitivity) are complete — all valid FDs can be derived. Use closure X^+ to find keys and test derivability.

  4. Normal forms are a ladder: 1NF (atomic) → 2NF (no partial deps) → 3NF (no transitive deps) → BCNF (every determinant is a superkey) → 4NF (no non-trivial MVDs).

  5. The running OrderLine example showed: partial deps caused product/customer data duplication in each order row → fixed by decomposing into four tables (2NF), then confirmed 3NF/BCNF.

  6. BCNF vs 3NF trade-off: BCNF eliminates all FD-based redundancy but may not preserve dependencies; 3NF always allows a lossless, dependency-preserving decomposition (use 3NF synthesis algorithm).

  7. A decomposition is lossless iff shared attributes form a key in at least one sub-relation.

## The Problem – A Single Table Approach

Imagine a university keeps all student enrollment data in a **single table** named `Enrollment`:

| **StudentID** | **StudentName** | **CourseID** | **CourseTitle** | **Instructor** | **Grade** |
|:---:|:---:|:---:|:---:|:---:|:---:|
| 101 | Ahmed | CS101 | Intro to CS | Dr. Sameer | A |
| 101 | Ahmed | MATH201 | Calculus II | Dr. Ibrahem | B+ |
| 102 | Sami | CS101 | Intro to CS | Dr. Layla | A- |
| 102 | Sami | PHY301 | Quantum Physics | Dr. Amani | C |

This looks simple — but it contains serious problems known as **anomalies**.

## Anomalies in Unnormalized Tables

### (a) Insertion Anomaly

**Problem:** Cannot insert certain data without other unrelated data.

Suppose a new course `CS202 – Data Structures` is added, but no student has enrolled yet.
You cannot insert `CourseID = CS202` and `CourseTitle = Data Structures` unless you also have a `StudentID`.
The course information depends on a student being enrolled.

| **StudentID** | **StudentName** | **CourseID** | **CourseTitle** | **Instructor** | **Grade** |
|:---:|:---:|:---:|:---:|:---:|:---:|
| 101 | Ahmed | CS101 | Intro to CS | Dr. Layla | A |
| 101 | Ahmed | MATH201 | Calculus II | Dr. Ibrahem | B+ |
| 102 | Sami | CS101 | Intro to CS | Dr. Layla | A- |
| 102 | Sami | PHY301 | Quantum Physics | Dr. Amani | C |
| **Null** | **Null** | **CS202** | **Data Structures** | **Null** | **Null** |

### (b) Deletion Anomaly

**Problem:** Deleting data unintentionally removes other important data.

If Ahmed drops `MATH201`, and he was the only student in that course, deleting his record also
deletes the course info (`MATH201`, `Calculus II`, `Dr. Ibrahem`).

| **StudentID** | **StudentName** | **CourseID** | **CourseTitle** | **Instructor** | **Grade** |
|:---:|:---:|:---:|:---:|:---:|:---:|
| 101 | Ahmed | CS101 | Intro to CS | Dr. Layla | A |
| ~~101~~ | ~~Ahmed~~ | ~~MATH201~~ | ~~Calculus II~~ | ~~Dr. Ibrahem~~ | ~~B+~~ |
| 102 | Sami | CS101 | Intro to CS | Dr. Layla | A- |
| 102 | Sami | PHY301 | Quantum Physics | Dr. Amani | C |

### (c) Update Anomaly

**Problem:** Redundant data leads to inconsistencies during updates.

Dr. Layla teaches `CS101`. Her name appears in **every row** where `CS101` is offered.
If Dr. Layla changes her name (e.g., to *Prof. Layla*), you must update every row with `CS101`.
If you miss one row, data becomes inconsistent.

| **StudentID** | **StudentName** | **CourseID** | **CourseTitle** | **Instructor** | **Grade** |
|:---:|:---:|:---:|:---:|:---:|:---:|
| 101 | Ahmed | CS101 | Intro to CS | **Prof. Layla** | A |
| 101 | Ahmed | MATH201 | Calculus II | Dr. Ibrahem | B+ |
| 102 | Sami | CS101 | Intro to CS | **Dr. Layla** ← inconsistent! | A- |
| 102 | Sami | PHY301 | Quantum Physics | Dr. Amani | C |

**Root cause:** a single row stores facts about *three separate entities* — students, courses, and
enrollments — all mixed together.

## Solution: Normalization

**Normalization** is the process of decomposing a table into smaller, well-structured tables to:

- **Eliminate redundancy** — the same data isn't stored multiple times unnecessarily
- **Avoid anomalies** — relationships between tables are clear and logical
- **Ensure data integrity** — queries run faster and are easier to maintain

We split the `Enrollment` table into three tables:

**Students**

| **StudentID** | **StudentName** |
|:---:|:---:|
| 101 | Ahmed |
| 102 | Sami |

**Courses**

| **CourseID** | **CourseTitle** | **Instructor** |
|:---:|:---:|:---:|
| CS101 | Intro to CS | Dr. Layla |
| MATH201 | Calculus II | Dr. Ibrahem |
| PHY301 | Quantum Physics | Dr. Amani |

**Enrollments**

| **StudentID** | **CourseID** | **Grade** |
|:---:|:---:|:---:|
| 101 | CS101 | A |
| 101 | MATH201 | B+ |
| 102 | CS101 | A- |
| 102 | PHY301 | C |

Now each anomaly disappears:

- **Adding a new course?** Just insert into `Courses` — no student needed.
- **A student drops a course?** Delete only from `Enrollments` — course data stays intact.
- **Instructor name changes?** Update one row in `Courses` — done.

## Functional Dependencies

### The Bridge Between Business Rules and Database Design

Before we can normalize, we need a precise language for describing *what determines what* in a
relation. That language is **functional dependencies (FDs)**.

Think of it like a deterministic mathematical function:

$$y = f(x) \quad \Longrightarrow \quad \text{knowing } x \text{ always gives you exactly one } y$$

The database equivalent is written $X \to Y$ and reads:

> **"For every valid instance of $X$, there is a unique value of $Y$ in the table."**

In other words, if two rows have the same $X$ value, they *must* have the same $Y$ value — no exceptions.

**Example:** A company assigns each employee a unique `EmpNo`.

$$SSN \to Name$$

- Meaning: if you give me the value of `SSN`, I can tell you the name of that employee.
- The expression $SSN \to Name$ is read as **"SSN defines Name"** or **"SSN implies Name."**
- But $Name \to SSN$? **No** — it would be inconsistent if two different employees happened to share the same name; their SSNs would differ, so `Name` cannot determine `SSN`.

::: callout-important
## 💡 FDs come from domain knowledge — not from data!

FDs are a characteristic of the **relation schema** itself. They describe rules that must hold for
**all possible data** in that schema — not just today's snapshot.

- ❌ Don't assume an FD just because it happens to hold in the current rows.
- ⚠️ An FD must hold for **every valid state** the relation could ever be in.
:::

### Types of Functional Dependencies

| Term | Meaning |
|------|---------|
| **Trivial FD** | $X \to Y$ where $Y \subseteq X$ (e.g., $\{A,B\} \to A$) — always true, carries no information |
| **Non-trivial FD** | $Y \not\subseteq X$ — the interesting kind |
| **Full FD** | $X \to Y$ and no proper subset of $X$ also determines $Y$ |
| **Partial FD** | A proper subset of $X$ already determines $Y$ — redundancy red flag for 2NF |
| **Transitive FD** | $X \to Y \to Z$ where $Y$ is not a key — redundancy red flag for 3NF |

---

### Discovering FDs from Stakeholders

FDs are discovered by asking domain experts — the people who *own* the business rules.

**Example — you ask the University Registrar:**

| **Question** | **Answer** | **FD Captured** |
|:---|:---|:---|
| "Is StudentID unique?" | "Yes!" | $StudentID \to StudentName$ |
| "Can CS301 have two titles?" | "No! Course title is fixed." | $CourseID \to CourseTitle$ |
| "Can one course have multiple instructors?" | "Not in the same term." | $(CourseID, Term) \to Instructor$ |
| "What determines a student's grade?" | "Their performance in a specific course." | $(StudentID, CourseID) \to Grade$ |

✅ These business rules become functional dependencies!

---

### FD Validation

An FD is **valid** (holds) when: for every pair of rows in the table that share the same LHS value,
they also share the same RHS value. Formally:

> $X \to Y$ holds iff for every two tuples $t_1, t_2$: if $t_1[X] = t_2[X]$ then $t_1[Y] = t_2[Y]$.

::: callout-note
## Example: FD Validation

Consider the relation $R(A, B, C, D)$ with the following instance:

| A | B | C | D |
|:---:|:---:|:---:|:---:|
| 1 | 1 | 2 | 3 |
| 1 | 2 | 2 | 3 |
| 1 | 3 | 2 | 3 |
| 2 | 4 | 5 | 6 |
| 5 | 6 | 7 | 8 |

Which of the following FDs are satisfied by this relation?

(a) $A \to B$ &emsp; (b) $A \to CD$ &emsp; (c) $AB \to CD$ &emsp; (d) $C \to D$ &emsp; (e) $B \to A$

(f) $BD \to AC$ &emsp; (g) $AD \to BC$ &emsp; (h) $D \to B$ &emsp; (i) $D \to C$ &emsp; (j) $C \to A$

{{< dstart summary="Solution" >}}

**(a) $A \to B$** — ❌ **Does not hold.**
For $A = 1$ there are three different $B$ values: 1, 2, and 3.

**(b) $A \to CD$** — ✅ **Holds.**
For every $A$ value there is exactly one $(C, D)$ pair:
$A=1 \Rightarrow (2,3)$, $A=2 \Rightarrow (5,6)$, $A=5 \Rightarrow (7,8)$.

**(c) $AB \to CD$** — ✅ **Holds.**
Every $(A,B)$ combination is unique (appears only once), so each maps to exactly one $(C,D)$.

**(d) $C \to D$** — ✅ **Holds.**
$C=2 \Rightarrow D=3$, $C=5 \Rightarrow D=6$, $C=7 \Rightarrow D=8$.

**(e) $B \to A$** — ✅ **Holds.**
Every $B$ value is unique in this instance, so it maps to a single $A$.

**(f) $BD \to AC$** — ✅ **Holds.**
Each $(B,D)$ combination appears at most once.

**(g) $AD \to BC$** — ❌ **Does not hold.**
For $(A,D) = (1,3)$ there are three $(B,C)$ pairs: $(1,2)$, $(2,2)$, $(3,2)$.

**(h) $D \to B$** — ❌ **Does not hold.**
For $D = 3$ there are three $B$ values: 1, 2, and 3.

**(i) $D \to C$** — ✅ **Holds.**
$D=3 \Rightarrow C=2$, $D=6 \Rightarrow C=5$, $D=8 \Rightarrow C=7$.

**(j) $C \to A$** — ✅ **Holds** in this instance.
$C=2 \Rightarrow A=1$, $C=5 \Rightarrow A=2$, $C=7 \Rightarrow A=5$. Each $C$ value maps to a unique $A$.

> ⚠️ Note: (e) and (j) hold only in *this particular instance*. Without a domain rule confirming
> them, they cannot be declared FDs of the schema.

:::

## Keys and Functional Dependencies

### Review of Keys

A **key** is a set of attributes that uniquely identifies a tuple (row) in a relation (table).

| Key Type | Definition |
|----------|-----------|
| **Super Key** | Any set of attributes that uniquely identifies a tuple. May contain extra attributes that are not necessary for uniqueness. |
| **Candidate Key** | A *minimal* super key — the smallest set of attributes that can uniquely identify a tuple. A table can have multiple candidate keys. |
| **Primary Key** | The candidate key chosen by the database designer to be the official unique identifier for the table. |

### Deriving Keys from FDs

The procedure moves from super keys down to candidate keys:

1. **Start** with a set of attributes $X$.
2. **Compute** $X^+$ (the closure of $X$ under the FD set $F$).
3. If $X^+$ includes **all attributes** in the relation, then $X$ is a **super key**.
4. If $X$ is **minimal** (no proper subset of $X$ is also a super key), then $X$ is a **candidate key**.

::: callout-note
**Why minimality matters:** If a super key is not minimal, it contains extra attributes that are
not required for uniqueness — and therefore it cannot be a candidate key.
:::

---

::: callout-note
## Example 1: Single Candidate Key

Consider $R(A, B, C, D)$ with the following functional dependencies:

- $A \to B$
- $B \to C$
- $C \to D$

Find all **super keys** and **candidate keys**.

{{< dstart summary="Solution" >}}

**Step 1 — Find super keys** by testing closures:

| Set $X$ | $X^+$ | Super key? |
|:-------:|:-----:|:----------:|
| $\{A\}$ | $\{A, B, C, D\}$ | ✓ |
| $\{A, B\}$ | $\{A, B, C, D\}$ | ✓ |
| $\{A, C\}$ | $\{A, B, C, D\}$ | ✓ |
| $\{A, D\}$ | $\{A, B, C, D\}$ | ✓ |
| $\{A, B, C\}$ | $\{A, B, C, D\}$ | ✓ |
| $\{A, B, D\}$ | $\{A, B, C, D\}$ | ✓ |
| $\{A, C, D\}$ | $\{A, B, C, D\}$ | ✓ |
| $\{A, B, C, D\}$ | $\{A, B, C, D\}$ | ✓ |
| $\{B\}$ | $\{B, C, D\}$ | ✗ |
| $\{C\}$ | $\{C, D\}$ | ✗ |
| $\{D\}$ | $\{D\}$ | ✗ |

**Step 2 — Check minimality:**

- $\{A\}$ is minimal → ✅ **Candidate key**
- $\{A, B\}$ — contains $\{A\}$ which is already a super key → ✗ not minimal
- $\{A, C\}$, $\{A, D\}$, $\{A,B,C\}$, … — all contain $\{A\}$ → ✗ not minimal

**Result:** The only candidate key is $\{A\}$.

{{< dstop >}}
:::

::: callout-note
## Example 2: Multiple Candidate Keys

Consider $R(A, B, C, D)$ with the following functional dependencies:

- $A \to B$
- $C \to D$
- $A, C \to D$
- $B, C \to A$

Determine the candidate keys.

{{< dstart summary="Solution" >}}

**Compute closures of candidate LHS sets:**

$\{A, C\}^+$:
- Start: $\{A, C\}$
- $A \to B$ → add $B$: $\{A, B, C\}$
- $C \to D$ → add $D$: $\{A, B, C, D\}$ = $R$ ✓ → **super key**
- Subsets: $\{A\}^+ = \{A,B\}$, $\{C\}^+ = \{C,D\}$ — neither covers $R$ → **minimal**
- → ✅ **Candidate key: $\{A, C\}$**

$\{B, C\}^+$:
- Start: $\{B, C\}$
- $B, C \to A$ → add $A$: $\{A, B, C\}$
- $C \to D$ → add $D$: $\{A, B, C, D\}$ = $R$ ✓ → **super key**
- Subsets: $\{B\}^+ = \{B\}$, $\{C\}^+ = \{C,D\}$ — neither covers $R$ → **minimal**
- → ✅ **Candidate key: $\{B, C\}$**

**Result:** Candidate keys are $\{A, C\}$ and $\{B, C\}$.

{{< dstop >}}
:::

## Example 3: Systematic Closure Method

Consider $R(A, B, C, D)$ with:

$$BC \to A, \quad AD \to B, \quad CD \to B, \quad AC \to D$$

Find **all** candidate keys of $R$.

{{< dstart summary="Solution" >}}

Compute the closure of each two-attribute combination:

| LHS | Derivation | $(\cdot)^+$ | Candidate Key? |
|:---:|:-----------|:---:|:---:|
| $(BC)^+$ | $BC \to A$ → $\{A,B,C\}$; then $AC \to D$ → $\{A,B,C,D\}$ | $R$ | ✅ |
| $(AD)^+$ | $AD \to B$ → $\{A,B,D\}$; no further FDs apply | $\{A,B,D\} \ne R$ | ✗ |
| $(CD)^+$ | $CD \to B$ → $\{B,C,D\}$; then $BC \to A$ → $\{A,B,C,D\}$ | $R$ | ✅ |
| $(AC)^+$ | $AC \to D$ → $\{A,C,D\}$; then $CD \to B$ → $\{A,B,C,D\}$ | $R$ | ✅ |

**Result:** Candidate keys are $\{B,C\}$, $\{C,D\}$, and $\{A,C\}$.

> Note: $\{A,D\}^+ = \{A,B,D\}$ — it cannot reach $C$, so it is not a super key.

{{< dstop >}}
:::

## Types of Functional Dependencies

### 1. Trivial Functional Dependency

A functional dependency $X \to Y$ is **trivial** if $Y \subseteq X$ — that is, $Y$ is a subset of $X$.

Trivial FDs always hold and carry no useful information about the data.

**Examples:**

- $\{StudentID, StudentName\} \to StudentName$ — trivial, because $StudentName$ is already in the LHS
- $\{A, B\} \to A$ — trivial
- $\{A, B\} \to \{A, B\}$ — trivial

---

### 2. Non-Trivial Functional Dependency

A functional dependency $X \to Y$ is **non-trivial** if $Y \not\subseteq X$ — at least one attribute on
the RHS is *not* already on the LHS.

These are the meaningful FDs that capture real business rules.

**Examples:**

- $StudentID \to StudentName$ — non-trivial: `StudentName` is not part of `StudentID`
- $CourseID \to CourseTitle, Instructor$ — non-trivial
- $\{A, B\} \to C$ — non-trivial if $C \notin \{A, B\}$

---

### 3. Transitive Functional Dependency

If $X \to Y$ and $Y \to Z$ both hold in a relation, then $X \to Z$ also holds. This is called a
**transitive dependency**. For a transitive dependency to exist, there must be **at least three
attributes** in the relation.

$$X \xrightarrow{\text{direct}} Y \xrightarrow{\text{direct}} Z \quad\Longrightarrow\quad X \xrightarrow{\text{transitive}} Z$$

**Example:**

In a student table:
- $StudentID \to DeptID$ (student belongs to a department)
- $DeptID \to DeptName$ (department has a name)
- Therefore: $StudentID \to DeptName$ — **transitive**, because `DeptID` is not a key

This is the red flag that 3NF eliminates.

---

### 4. Full Functional Dependency

A functional dependency $X \to Y$ is **full** if removing *any single attribute* from $X$ means
the dependency no longer holds. Every attribute in $X$ is necessary.

**Example:**

Consider an `Enrollment` table with composite key $\{StudentID, CourseID\}$:

- $\{StudentID, CourseID\} \to Grade$ — **full**, because:
  - $StudentID \to Grade$? ❌ No — the same student can get different grades in different courses
  - $CourseID \to Grade$? ❌ No — different students get different grades for the same course
  - Both attributes are required → **full FD**

---

### 5. Partial Functional Dependency

A functional dependency $A \to B$ is **partial** if some attribute in $A$ can determine $B$ on its
own, without needing the entire set $A$.

Partial dependencies only arise when the key is **composite** (more than one attribute).

**Example:**

Same `Enrollment` table with composite key $\{StudentID, CourseID\}$:

- $\{StudentID, CourseID\} \to StudentName$ — **partial**, because:
  - $StudentID \to StudentName$? ✅ Yes — student name depends only on the student, not the course
  - `CourseID` is irrelevant for determining `StudentName`

| FD | Type | Why |
|:---|:----:|:----|
| $\{StudentID, CourseID\} \to Grade$ | Full | Both attributes needed |
| $\{StudentID, CourseID\} \to StudentName$ | Partial | Only `StudentID` needed |
| $\{StudentID, CourseID\} \to CourseTitle$ | Partial | Only `CourseID` needed |

Partial dependencies cause the redundancy that **2NF** eliminates by decomposing the table.

## Normalization

**Normalization** is the systematic approach of effectively designing a database so that it
minimizes data redundancy and inconsistency. It is generally done through a series of steps called
**normal forms (NF)**.

Each normal form builds on the previous one — a relation in a higher NF automatically satisfies
all lower NFs:

$$1NF \;\subset\; 2NF \;\subset\; 3NF \;\subset\; BCNF \;\subset\; 4NF \;\subset\; 5NF$$

| Normal Form | Key Requirement | What it Eliminates |
|:---:|:---|:---|
| **1NF** | All attribute values are atomic | Multi-valued / repeating groups |
| **2NF** | 1NF + no partial FDs on any candidate key | Redundancy from partial dependencies |
| **3NF** | 2NF + no transitive FDs (with prime-attr exception) | Transitive dependencies via non-key attributes |
| **BCNF** | Every FD determinant is a superkey | All non-trivial FD-based redundancy |
| **4NF** | BCNF + no non-trivial MVDs | Multi-valued dependency redundancy |
| **5NF** | 4NF + no non-trivial join dependencies | Decomposition artifacts |

---

### First Normal Form (1NF)

**Definition:** A relation is in 1NF if:

- Every attribute contains only **atomic** (single-valued, indivisible) values
- There are no repeating groups or multi-valued attributes
- There is a **primary key** that uniquely identifies each row

::: callout-note
## Example: Violating 1NF

A student table stores multiple courses in one cell:

| StudentNo | StudentName | Courses |
|:---:|:---:|:---:|
| S1 | Ahmed | DS, Algorithms |
| S2 | Hussein | Databases |

`Courses` is **not atomic** — it holds multiple values in one cell. This violates 1NF.

{{< dstart summary="Solution: Convert to 1NF" >}}

Split into separate rows so each cell holds one value:

| **StudentNo** | **StudentName** | **CourseNo** | **CourseName** |
|:---:|:---:|:---:|:---:|
| S1 | Ahmed | CS101 | Data Structures |
| S1 | Ahmed | CS102 | Algorithms |
| S2 | Hussein | CS301 | Databases |

- Each cell now holds exactly one value ✅
- Primary key: `{StudentNo, CourseNo}` uniquely identifies each row ✅

> Note: `StudentName` is now repeated for Ahmed. This redundancy is addressed in 2NF.

{{< dstop >}}
:::

---

### Second Normal Form (2NF)

**Definition:** A relation is in 2NF if:

- It is already in **1NF**, AND
- Every non-prime attribute is **fully functionally dependent** on every candidate key

> 2NF is only relevant when the primary key is **composite**. A relation with a single-attribute
> primary key is automatically in 2NF if it is in 1NF.

A **partial dependency** exists when a non-key attribute depends on only *part* of a composite key.
2NF eliminates all partial dependencies.

::: callout-note
## Example: Violating 2NF

Using the 1NF table from above with composite key `{StudentNo, CourseNo}`:

| **StudentNo** | **StudentName** | **CourseNo** | **CourseName** | **InstructorNo** | **Grade** |
|:---:|:---:|:---:|:---:|:---:|:---:|
| S1 | Ahmed | CS101 | Data Structures | I1 | A |
| S1 | Ahmed | CS102 | Algorithms | I2 | B+ |
| S2 | Hussein | CS301 | Databases | I3 | A- |

Partial dependencies present:

- $StudentNo \to StudentName$ — depends only on `StudentNo`, not `CourseNo`
- $CourseNo \to CourseName, InstructorNo$ — depends only on `CourseNo`, not `StudentNo`

Only $\{StudentNo, CourseNo\} \to Grade$ is a **full** dependency.

{{< dstart summary="Solution: Convert to 2NF" >}}

Decompose by moving each partial dependency to its own table:

**Students** (key: `StudentNo`)

| **StudentNo** | **StudentName** |
|:---:|:---:|
| S1 | Ahmed |
| S2 | Hussein |

**Courses** (key: `CourseNo`)

| **CourseNo** | **CourseName** | **InstructorNo** |
|:---:|:---:|:---:|
| CS101 | Data Structures | I1 |
| CS102 | Algorithms | I2 |
| CS301 | Databases | I3 |

**Enrollments** (key: `{StudentNo, CourseNo}`)

| **StudentNo** | **CourseNo** | **Grade** |
|:---:|:---:|:---:|
| S1 | CS101 | A |
| S1 | CS102 | B+ |
| S2 | CS301 | A- |

All non-key attributes now depend on the **whole** key of their table. ✅

{{< dstop >}}
:::

---

### Third Normal Form (3NF)

**Definition:** A relation is in 3NF if:

- It is already in **2NF**, AND
- For every non-trivial FD $X \to A$: either $X$ is a superkey, **or** $A$ is a prime attribute

A **transitive dependency** exists when a non-key attribute determines another non-key attribute:
$Key \to Y \to Z$ where $Y$ is not a key. 3NF eliminates these.

::: callout-note
## Example: Violating 3NF

Suppose the `Courses` table from 2NF also stores instructor details:

| **CourseNo** | **CourseName** | **InstructorNo** | **InstructorName** | **InstructorLocation** |
|:---:|:---:|:---:|:---:|:---:|
| CS101 | Data Structures | I1 | Dr. Ali | Building A |
| CS102 | Algorithms | I2 | Dr. Sara | Building B |
| CS301 | Databases | I1 | Dr. Ali | Building A |

Transitive dependency:

$$CourseNo \to InstructorNo \to InstructorName, InstructorLocation$$

`InstructorNo` is not a candidate key of `Courses`, so `InstructorName` and `InstructorLocation`
transitively depend on `CourseNo`.

{{< dstart summary="Solution: Convert to 3NF" >}}

Move the transitive dependency to its own table:

**Courses** (key: `CourseNo`)

| **CourseNo** | **CourseName** | **InstructorNo** |
|:---:|:---:|:---:|
| CS101 | Data Structures | I1 |
| CS102 | Algorithms | I2 |
| CS301 | Databases | I1 |

**Instructors** (key: `InstructorNo`)

| **InstructorNo** | **InstructorName** | **InstructorLocation** |
|:---:|:---:|:---:|
| I1 | Dr. Ali | Building A |
| I2 | Dr. Sara | Building B |

Now `InstructorName` and `InstructorLocation` depend directly on their key `InstructorNo`. ✅
Updating Dr. Ali's location requires changing **one row** only.

{{< dstop >}}
:::

---

### Boyce-Codd Normal Form (BCNF)

**Definition:** A relation is in BCNF if:

- It is already in **3NF**, AND
- For **every** non-trivial FD $X \to Y$: $X$ must be a **superkey**

BCNF is stricter than 3NF — it removes the "prime attribute" exception. A relation can be in 3NF
but not BCNF when there are multiple overlapping candidate keys.

::: callout-note
## Example: 3NF but not BCNF

```
Enrolment(Student, Course, Teacher)
```

FDs:
- $\{Student, Course\} \to Teacher$ — a student in a course has one teacher
- $Teacher \to Course$ — each teacher teaches exactly one course

Candidate keys: $\{Student, Course\}$ and $\{Student, Teacher\}$

Check: $Teacher \to Course$ — `Teacher` is **not** a superkey → **BCNF violated**

But `Course` is a prime attribute (part of candidate key $\{Student, Course\}$) → **3NF holds**

{{< dstart summary="Solution: Convert to BCNF" >}}

Decompose on the violating FD $Teacher \to Course$:

**TeacherCourse** (key: `Teacher`)

| **Teacher** | **Course** |
|:---:|:---:|
| Dr. Ali | Databases |
| Dr. Sara | Algorithms |

**StudentTeacher** (key: `{Student, Teacher}`)

| **Student** | **Teacher** |
|:---:|:---:|
| Ahmed | Dr. Ali |
| Yaser | Dr. Sara |

Both tables are now in BCNF. ✅

> Trade-off: the FD $\{Student, Course\} \to Teacher$ can no longer be verified in a single table —
> it requires a join. This is the dependency-preservation cost of BCNF decomposition.

{{< dstop >}}
:::

### Worked Example: Full Normalization (1NF → 3NF)

The following example applies all three normal forms step by step to the university enrollment
scenario.

**Starting table** — `Enrollment` with composite key `{StudentID, CourseID}`:

| StudentID | StudentName | CourseID | CourseTitle | Instructor | Grade |
|:---:|:---:|:---:|:---:|:---:|:---:|
| 101 | Ahmed | CS101 | Intro to CS | Dr. Sameer | A |
| 101 | Ahmed | MATH201 | Calculus II | Dr. Ibrahem | B+ |
| 102 | Sami | CS101 | Intro to CS | Dr. Layla | A- |
| 102 | Sami | PHY301 | Quantum Physics | Dr. Amani | C |

**FDs:**

```
StudentID  → StudentName
CourseID   → CourseTitle, Instructor
{StudentID, CourseID} → Grade
```

#### Step 1 — Is it in 1NF?

Every cell contains a single atomic value and there is a primary key. ✅ **Already in 1NF.**

#### Step 2 — Check for 2NF

The key is composite `{StudentID, CourseID}`. Check for partial dependencies:

| FD | Partial? |
|:---|:---:|
| $StudentID \to StudentName$ | ✅ Partial — only `StudentID` needed |
| $CourseID \to CourseTitle, Instructor$ | ✅ Partial — only `CourseID` needed |
| $\{StudentID, CourseID\} \to Grade$ | ✗ Full — both needed |

**Not in 2NF.** Decompose:

```
Students(StudentID PK, StudentName)
Courses(CourseID PK, CourseTitle, Instructor)
Enrollments(StudentID FK, CourseID FK, Grade)   -- PK = {StudentID, CourseID}
```

✅ **Now in 2NF** — no partial dependencies remain.

#### Step 3 — Check for 3NF

Check each table for transitive dependencies:

- `Students(StudentID, StudentName)` — no transitive FD. ✅
- `Enrollments(StudentID, CourseID, Grade)` — no transitive FD. ✅
- `Courses(CourseID, CourseTitle, Instructor)` — does `Instructor → CourseTitle`? Only if each
  instructor teaches exactly one course. If that is a business rule, it is a transitive FD and
  must be decomposed further. Otherwise ✅ in 3NF as-is.

**Final 3NF schema:**

```{mermaid}
%%| eval: true
%%| echo: false
erDiagram
    Students {
        int         StudentID PK
        varchar(50) StudentName
    }
    Courses {
        varchar(10) CourseID PK
        varchar(100) CourseTitle
        varchar(50) Instructor
    }
    Enrollments {
        int         StudentID FK
        varchar(10) CourseID FK
        char(2)     Grade
    }
    Students ||--o{ Enrollments : "enrolls in"
    Courses  ||--o{ Enrollments : "enrolled by"
```

### Example 1 — Simple: Identify the Normal Form

::: callout-note
## Question

Given the relation $R(A, B, C, D, E)$ with $F = \{AB \to CD,\ B \to C\}$.
Is $R$ in 2NF? If not, convert it to 2NF.

{{< dstart summary="Solution" >}}

**Step 1 — Find the candidate key.**

Attributes $A$, $B$, $D$, $E$ do not appear on any RHS, so they must be part of every candidate key.
$\{A, B, D, E\}^+$:

- $AB \to CD$ → add $C, D$: $\{A,B,C,D,E\}$ = $R$ ✓

Candidate key: $\{A, B, D, E\}$

**Step 2 — Check for partial dependencies.**

Non-prime attributes: $C$.

- $B \to C$ — $B$ is a proper subset of the key $\{A,B,D,E\}$ → **partial dependency** ✗

**Conclusion:** $R$ is **not in 2NF**.

**Step 3 — Decompose.**

Move the partial dependency $B \to C$ to its own relation:

- $R_1(B, C)$ — key: $B$
- $R_2(A, B, D, E)$ — key: $\{A, B, D, E\}$

Both $R_1$ and $R_2$ are in **2NF**. ✅

{{< dstop >}}
:::

$$Courses(\underline{CourseNo},\ CoursName,\ InstrNo)$$
$$Instructors(\underline{InstrNo},\ InstrName,\ InstrLoc)$$
$$Enrollments(\underline{StudNo},\ \underline{CourseNo},\ Grade)$$

**Step 4 — Verify 3NF:**

| Table | FD | 3NF? |
|:---|:---|:---:|
| $Courses$ | $CourseNo \to CoursName, InstrNo$ | ✅ key → non-key |
| $Instructors$ | $InstrNo \to InstrName, InstrLoc$ | ✅ key → non-key |
| $Enrollments$ | $\{StudNo, CourseNo\} \to Grade$ | ✅ key → non-key |

✅ All tables are now in 3NF.

**Answer to (1):** The original relation was in **1NF only** (violated 2NF due to partial dependency).

### Example 6 — Hard: Full Normalization (1NF → BCNF)

::: callout-note
## Question

A hospital stores patient visit data in one table:

$$Visit(PatientID,\ PatientName,\ DoctorID,\ DoctorName,\ Speciality,\ RoomNo,\ RoomType,\ VisitDate,\ Diagnosis)$$

FDs:

- $PatientID \to PatientName$
- $DoctorID \to DoctorName,\ Speciality$
- $RoomNo \to RoomType$
- $\{PatientID, DoctorID, VisitDate\} \to Diagnosis,\ RoomNo$
- $Speciality \to DoctorID$ *(each speciality has one assigned doctor)*

Normalize to BCNF.

{{< dstart summary="Solution" >}}

**1NF:** All attributes are atomic. ✅

**2NF:** Candidate key is $\{PatientID, DoctorID, VisitDate\}$. Partial dependencies:

| FD | Partial? |
|:---|:---:|
| $PatientID \to PatientName$ | ✅ partial |
| $DoctorID \to DoctorName, Speciality$ | ✅ partial |

**Decompose to 2NF:**

$$Patients(\underline{PatientID},\ PatientName)$$
$$Doctors(\underline{DoctorID},\ DoctorName,\ Speciality)$$
$$Visits(\underline{PatientID},\ \underline{DoctorID},\ \underline{VisitDate},\ RoomNo,\ Diagnosis)$$

---

**3NF:** Check `Visits` for transitive dependencies:

$$\{PatientID, DoctorID, VisitDate\} \to RoomNo \to RoomType$$

`RoomNo` is not a key → **transitive dependency**.

**Decompose:**

$$Rooms(\underline{RoomNo},\ RoomType)$$
$$Visits(\underline{PatientID},\ \underline{DoctorID},\ \underline{VisitDate},\ RoomNo,\ Diagnosis)$$

Also check `Doctors`:

$$DoctorID \to Speciality \quad\text{and}\quad Speciality \to DoctorID$$

Both `DoctorID` and `Speciality` are candidate keys of `Doctors` → no transitive dependency. ✅

---

**BCNF check on `Doctors`:**

FDs on $Doctors(DoctorID, DoctorName, Speciality)$:

- $DoctorID \to DoctorName, Speciality$ — `DoctorID` is a superkey ✅
- $Speciality \to DoctorID$ — is `Speciality` a superkey?
  - $Speciality^+ = \{Speciality, DoctorID, DoctorName\}$ = all attributes ✅ superkey

Both FD determinants are superkeys → `Doctors` is in **BCNF**. ✅

**BCNF check on all other tables:** Each has a single-attribute or composite key and no extra FD determinants → all in BCNF. ✅

**Final BCNF schema:**

| Table | Key | Non-key attributes |
|:---|:---:|:---|
| $Patients$ | $PatientID$ | $PatientName$ |
| $Doctors$ | $DoctorID$ (or $Speciality$) | $DoctorName,\ Speciality$ |
| $Rooms$ | $RoomNo$ | $RoomType$ |
| $Visits$ | $\{PatientID, DoctorID, VisitDate\}$ | $RoomNo,\ Diagnosis$ |

✅ All tables in BCNF.

## Normal Form Summary

| Normal Form | Condition | What it eliminates |
|------------|-----------|-------------------|
| **1NF** | All attributes atomic | Multi-valued / repeating groups |
| **2NF** | 1NF + no partial FDs | Redundancy from composite-key partial deps |
| **3NF** | 2NF + no transitive FDs (with prime-attr exception) | Transitive deps via non-key attributes |
| **BCNF** | Every FD determinant is a superkey | All non-trivial FD redundancy |
| **4NF** | BCNF + no non-trivial MVDs | Multi-valued dependency redundancy |
| **5NF** | 4NF + no non-trivial join dependencies | Decomposition artifacts |

::: callout-important
## 3NF vs BCNF Trade-off

| Property | 3NF | BCNF |
|---------|-----|------|
| Lossless decomposition | ✓ | ✓ |
| Dependency preservation | ✓ (always) | ✗ (may lose some FDs) |
| Eliminates all FD-based redundancy | Partial | Yes |

Use BCNF when possible; fall back to 3NF when you must preserve a specific dependency.
:::

## BCNF Decomposition — A Case Where 3NF ≠ BCNF

The BCNF and 3NF distinction matters when there are **multiple overlapping candidate keys**.

**Classic example:**

```
Enrolment(Student, Course, Teacher)
```

FDs:
- `{Student, Course} → Teacher` (a course has exactly one teacher per student)
- `Teacher → Course` (a teacher teaches exactly one course)

Candidate keys:
- `{Student, Course}` — covers all columns
- `{Student, Teacher}` — covers all columns (because `Teacher → Course`)

Check for BCNF violations:
- `Teacher → Course`: determinant `Teacher` is NOT a superkey → **BCNF violated**

Check for 3NF violations:
- `Teacher → Course`: `Course` is a prime attribute (member of candidate key `{Student, Course}`) → **3NF satisfied** (prime-attr exception)

So `Enrolment` is in 3NF but **not** in BCNF.

**BCNF decomposition:**

```
TeacherCourse(Teacher PK, Course)       -- FD: Teacher → Course
StudentTeacher(Student, Teacher)        -- PK: {Student, Teacher}
```

Trade-off: the FD `{Student, Course} → Teacher` can no longer be checked in a single table — it requires a join.
That is the dependency-preservation loss inherent to BCNF decomposition.

## Multivalued Dependencies and 4NF

A **multivalued dependency (MVD)** $X \twoheadrightarrow Y$ holds when, for each value of $X$,
the set of $Y$ values is independent of the remaining attributes $Z$.

**Example:**

```
EmployeeSkillHobby(Ssn, Skill, Hobby)
```

An employee has a set of skills and a set of hobbies, and these are independent of each other.
MVDs: `Ssn ↠ Skill` and `Ssn ↠ Hobby`.

This causes redundancy: each (Ssn, Skill) pair must be repeated for each Hobby.

| Ssn | Skill | Hobby |
|-----|-------|-------|
| 111 | Java | Chess |
| 111 | Java | Soccer |
| 111 | SQL | Chess |
| 111 | SQL | Soccer |

**4NF** requires that every non-trivial MVD $X \twoheadrightarrow Y$ has $X$ as a superkey.

**Fix:**

```
EmployeeSkill(Ssn, Skill)
EmployeeHobby(Ssn, Hobby)
```

## Canonical Cover (Minimal Cover)

The **canonical cover** $F_c$ of an FD set $F$ is an equivalent, minimal FD set:

1. Every FD has a **single attribute on the right side** (decompose all compound RHS)
2. No FD has a **redundant attribute on the left side** (check if dropping a LHS attribute leaves the FD derivable)
3. No FD is **redundant overall** (check if removing the whole FD leaves it derivable from the rest)

**Why compute $F_c$?** The 3NF synthesis algorithm uses $F_c$ to generate the minimal, dependency-preserving, lossless schema.

---

## Dependency Preservation

A decomposition $\{R_1, R_2, \ldots, R_k\}$ of $R$ is **dependency-preserving** iff every FD in $F^+$ can be verified in at least one $R_i$ without performing a join:

$$
\left(\bigcup_{i=1}^{k} F_i\right)^+ = F^+
$$

where $F_i$ = projection of $F$ onto $R_i$.

BCNF decompositions may not be dependency-preserving (as shown in §9.7).
The **3NF synthesis algorithm** always produces a lossless, dependency-preserving decomposition.

## Chapter Summary

::: callout-important
## Key Takeaways — Chapter 9

1. **Update anomalies** (insertion, deletion, modification) arise whenever a table stores facts about
   multiple unrelated entities. Normalization eliminates the root cause.

2. A **functional dependency** $X \to Y$ means knowing $X$ always determines $Y$.
   Key types: full (depends on whole key), partial (depends on subset), transitive ($X \to Y \to Z$).

3. **Armstrong's Axioms** (Reflexivity, Augmentation, Transitivity) are complete —
   all valid FDs can be derived. Use **closure** $X^+$ to find keys and test derivability.

4. **Normal forms** are a ladder: 1NF (atomic) → 2NF (no partial deps) → 3NF (no transitive deps)
   → BCNF (every determinant is a superkey) → 4NF (no non-trivial MVDs).

5. The **running OrderLine example** showed: partial deps caused product/customer data duplication in
   each order row → fixed by decomposing into four tables (2NF), then confirmed 3NF/BCNF.

6. **BCNF vs 3NF trade-off**: BCNF eliminates all FD-based redundancy but may not preserve dependencies;
   3NF always allows a lossless, dependency-preserving decomposition (use 3NF synthesis algorithm).

7. A decomposition is **lossless** iff shared attributes form a key in at least one sub-relation.
:::
